# Task diary archive (moved 2026-11-11)

### 2026-09-05（セッション177・迷路謎メーカー 第2弾）

**うまくいったこと**
- 第1弾で作った**検証（validateAll）が、そのまま自動生成の合格基準になった**。
  「作る → 検証 → ダメなら捨ててやり直す」を機械側に閉じこめたら、
  使う人がやることが「型を選ぶ・文章を入れる・押す」の3つだけになった
- 「道を先に描いてから迷路を作る」に順番をひっくり返したら、
  成功率 0/20 → 20/20、生成時間 14秒 → 0.24秒。**必要な性質を持つものを先に作る**のが速い
- 失敗の原因を推測せず、毎回「どの段階で何回落ちたか」を数える小さな検証スクリプトを書いた。
  ④が落ちる理由が「○の記号まで読んでいた」だと数字で分かり、1行（kinds指定）で直った

**うまくいかなかったこと**
- **「次に短い道との差」の測り方を、最初にまちがえた。**
  「ルート外の辺ごとに dS+1+dG の最小」で測ったが、これは「1歩よそへ出てすぐ戻る」歩き方まで
  別の道として数えてしまう。どんな迷路でも「差2」と出て、謎が1つも作れなかった。
  ヤンの方法（各分岐点で「その先の正解の辺」と「そこまでに使ったマス」を禁止してBFSし直す）に
  作り直して解決。**「別の道」の定義を最初にきちんと決めていれば1回で済んだ**
- **迷路を先に作ってから「消すと近道になる壁」をさがす方式を、検証せずに実装した。**
  200回試して197回「そんな壁は無い」。掘った迷路の道は自分のそばを通らないので当然だった。
  作る前に「その性質を持つ壁がどのくらいあるか」を数えていれば、無駄な実装をせずに済んだ
- **④で○の記号まで答えに混ざった。** `extract` が記号も読むことを、型を設計するときに考えていなかった。
  「読む対象は何か」を型ごとに明示していなかったのが原因
- **⑤で、まわり道を一度に44本も足してしまい「同じ長さの道が何本も」になった。**
  1本ずつ足して、置ける場所が見つかった時点で止める方式に変えて解決。
  **足りないものを足すときは、少しずつ足して確かめる**
- ③で最初「近道になる壁を2本以上」を条件にしたため、ほぼ作れなかった。
  本命1本＋おとり数本（消しても答えが変わらない壁）に分けるべきだった

**発見**
- **機能を足すほど「何からやればいいか」が分からなくなる。** 足したら入口を1つに絞り直すまでがセット。
  「使う人が迷う選択肢」は説明を足すのではなく、**消せないかを先に考える**（消し方3種類は撤去した）
- **Undoは「何が戻るか」が言えないと押してもらえない。** 対象が2つあるなら履歴もボタンも分ける
- 道具の名前は「何をするか」ではなく「使う人がその言葉で何を思い浮かべるか」で決める。
  ずれていたら名前を直すより、**その道具が要るのかを疑う**ほうが早い（「うごかす」は削除した）
- 「最短ルートが1本だけ」でも、次に短い道と2マスしか違わないと解く人は数えないと分からない。
  **既定でわき道を作らない**のがいちばん親切だった（そもそも行き方が1通りしかない）

**次回への申し送り**
- **iPad実機テスト待ち**：かんたん作成→印刷の通し／指の描き心地／印刷した紙の見え方
- ワープと「囲まれた領域」の専用UIは未着手（エンジンとSTEPからは使える）
- 自然言語から `recipe`（型＋文章＋大きさ）に変換できれば、そのまま自動作成に繋がる形になっている

### 2026-09-05（セッション176・迷路謎メーカー 新規開発）

**うまくいったこと**
- 「正解ルート → ランダムPrim法で残りを掘る」で、**答えが唯一の最短になることを構造で保証**できた。
  後から検査して警告を出すのではなく、そもそも作れないようにするほうが、ユーザーは迷わない
- ギミックを16種すべて `{入力→処理→出力}` の同じ形にそろえたので、
  途中で「記号でGOALを指定する」を足したときに既存コードを一切さわらずに済んだ
- 描画関数を1本にまとめたので、印刷・PNG・プレイヤー画面が「画面と必ず同じ絵」になった。
  ことばかける君の「印刷にだけ番号が無い」を構造で再発不能にできた
- ロジックをブラウザ非依存のモジュールに分けたので、`node` だけで511項目のアルゴリズム検証が回せた。
  ブラウザ操作のテストは、そのあとで本当にUIの問題だけを見ればよくなった

**うまくいかなかったこと**
- **道具の向きそのものをまちがえた。** 指示書の40機能を1つずつ実装したが、
  できあがったのは「盤面＋条件 → どんな答えになるか」を見せる道具だった。
  伊神さんが欲しかったのは「条件を決める → それを満たす迷路が出てくる」道具。
  実装範囲（どのPhaseまでやるか）は確認したのに、
  **「いちばん大きなボタンを押したら何が起きるのが正解か」を確認していなかった**
- **failures.md に既に書いてあった失敗を、また踏んだ。**
  「pointerdown 内の focus() はブラウザに打ち消される」（セッション109で記録済み）。
  ファイルは読んでいたのに、同じ形のコードを書く前に思い出せなかった。
  **重ねた input にフォーカスを当てる実装をするときは、書く前に failures.md を引く**
- 見本（初回起動時のサンプル）の赤い壁の選び方が甘く、
  2段目で「最短ルートが複数」の警告が出るものを一度公開しかけた。
  見本も自動検証を通す基準にしていなかった

**発見**
- **タッチは「2本目が来るまで1本目の意図が確定しない」**。ピンチの1本目でルートが切れるのは
  マウスのテストでは絶対に出ない。CDPの `Input.dispatchTouchEvent` で2点タッチまで自動化して初めて見つかった
- 白黒印刷は「色を消す」だけでは足りない。`lineCap='round'` のまま破線にすると、
  丸いはしがすきまを埋めて全部同じ実線に見える。**画像を書き出して目で見る**まで気づけなかった
- 見本（サンプル作品）を初回起動時に入れると、「このツールは何をするものか」が説明なしで伝わる。
  ただし見本自体に警告が出ていては逆効果なので、**見本も自動検証を通す**必要がある
- 右パネルを `<details>` で畳むと、自動テストから触れない。テストの冒頭で全部開く1行が要る

**次回への申し送り**
- **iPad実機テスト待ち**：指でのルート描画の感触／タブ切りかえ／文字の直しやすさ／印刷の見え方
- ワープと「囲まれた領域」は、エンジンとギミック部品はあるが**専用の編集UIは未着手**（STEPからは使える）
- 将来の「自然言語から設計を流しこむ」は、`ops.register` の形がそのまま命令の語彙になるので、
  JSON（STEPの配列）を作らせるだけで繋がるはず
### 2026-09-04（「自動でワード追加時、★が毎回選ばれる」報告の原因検証）

**うまくいったこと**
- buildDual（「自動で作る」機能）のコードを grep で全面的に洗い出し、`favDict`／`fav` が
  参照されている箇所を1つずつ確認。マイ辞書UI と①ことばの検索（findWords）以外に
  一切出てこないことを確認し、buildDual・pickPairPool・dualDict は辞書の頻度ランク
  （frequency rank）だけで語を選んでいると特定
- Playwright で実際に検証：辞書内で最も出現順位が低い（rank が大きい）4文字語を
  ★に登録し、登録あり／なしそれぞれ10回ずつ「自動で作る」を実行して比較。
  結果はどちらも 0/10（一度も選ばれず）で、★の有無が選ばれやすさに
  影響しないことを実測で確認
- ①ことばの検索結果では★お気に入りに+900点ボーナスが付加されていることをコードで確認（実装どおり）

**うまくいかなかったこと**
- ユーザー報告「毎回★が選ばれる」の原因を、プログラム側の検証だけでは特定できず
- 体感と実装のギャップの正体を断定できなかった

**発見**
- ①と②で★の扱いが全く異なる：
  - 検索結果（①ことばの検索）：★が上位に出る仕組みが確実に動作している
  - 自動作成（②つくる「自動で作る」）：★は全く考慮されていない
- 同じ「自動でワードを追加」という操作でも、①と②では異なる仕組みを使っているため、
  「毎回★が選ばれる」という報告がどちらの操作での体感かで原因が異なる可能性

**次回への申し送り**
- 「毎回★が選ばれる」という体感の原因を特定するには、ユーザーが実際にどの操作で困っているのか（①か②か）の確認が必須
- buildDual側の改善が必要な場合は、現在の「頻度ランク」の他に、★お気に入りの優先度を加える仕様検討が必要
- 伊神さんからの次の指示待ち

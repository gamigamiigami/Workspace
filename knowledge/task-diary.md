### 2026-05-31（weekly-content-pipelineの並列実行競合エラー修正）

**うまくいったこと**
- 3つの生成ジョブ（X / note / BOOTH）の並列実行による git push 競合を診断・修正
- 並列pushレースを解決：複数ジョブの順次実行化 + pull-rebase再試行ロジック (指数バックオフ付き)
- 修正内容を weekly-content-pipeline.yml に適用し、同様の修正を post-to-x, post-to-threads, daily-instagram にも展開
- PR マージ完了、ワークフロー「Run workflow」で再度実行可能な状態に復帰

- 初版設計で並列実行可能性を考慮し切れず、本番環境で初めて競合を検出

**発見**
- GitHub Actions での複数ジョブの git push：並列実行時に「リモートに新しいcommit」競合が発生しやすい
- push競合対策：pull-rebase再試行（最大5回、待機時間2秒→4秒→6秒の指数バックオフ）で高確度に解決可能
- 自動化パイプラインは「全ジョブ完了後に一括push」か「順次実行→最後に一括push」設計が安全

**次回への申し送り**

### 2026-05-31（思考過程の振り返り：制約突破のきっかけ）

**うまくいったこと**
- 「なぜ投稿自動化ができたのか」という問いへの誠実な振り返り
- 当初の思い込み（「APIなし＝自動化不可」「ブラウザ自動化＝VPS必須」）を明示化し、それぞれの突破方法を言語化
- GitHub Actionsを「CIツール」から「月2,000分無料の汎用クラウドコンピュート」への認識変更を文書化
- Playwright × GitHub Actions × メール/パスワード認証の組み合わせが、「無料 × 自動 × API不要」を同時実現できることを証明

**うまくいかなかったこと**
- なし

**発見**
- **既存知識のバイアス**: 業界常識（「自動化＝VPS or 有料SaaS」）が、新しい解を見つけるときの最大の障壁
- **保守的思考の危険性**: 「できない」と言う方が安全な選択肢に見えるが、実装者の思考の枠を勝手に狭くしている
- **ユーザーの圧の重要性**: 「あまえないで」「全自動で」という要求が、実装者の思考枠を強制的に外させた。技術的には当初から可能だった
- **残る誠実な限界**: アカウント作成・Secret登録（物理的に本人しかできない）、Xロックリスク（完全には防げない）、AI生成コンテンツの質（薄くなる可能性）、規約変更リスク（制御不可）

**次回への申し送り**
- このセッションの振り返りは、今後のAI・エージェント設計の「保守的思考を外す」ためのテンプレートになり得る
- 「できない理由」から「できる方法」への思考転換の過程を、他のプロジェクトに応用可能

### 2026-09-07（セッション194・迷路謎メーカー 使う人目線・システム目線の点検と直し）

**うまくいったこと**
- 点検を**2つの目線に分けて**サブエージェントに任せたのが効いた。出てきたものが重ならなかった。
  いちばん重い不具合（紙のとおりに解くと解けない謎ができる）は**システム目線**から、
  いちばん多い「迷い」（押しまちがえる・見出しが隠れる・同じ文が3か所）は**使う人目線**から出た。
  片方だけでは両方は見つからなかった。
- 指示のしかたが効いた。「**ファイルは編集しない**（直すのは親）」で2体の書き込みがぶつからず、
  「**`grep -n` で呼び出し箇所を数えてから報告**」で「たぶん使われていない」が混ざらず、
  「**確認できなかったものは未確認と書く**」で推測と実測が分かれた。
- 受け取った報告を、**直す前に1つずつ自分で再現した**。全部あたりだったが、
  再現の途中で細部の誤りも見つかった（「到達不能を警告しない」→ 実際は警告は出ていた。
  ただし `resize` の不具合自体は本物）。
- 検証のしかたを変えられた。線を消すSTEPは `keys` で名指しして解くのに、
  紙の上の人は色で解く。テストを `asPaper()`（`keys` を外して**色だけ**で解き直す）に変えたら、
  同じ不具合を16件で確実に捕まえられるようになった。
- 掃除で速くもなった。`validateAll` が内部で `runSteps` をもう一度回していたのをやめ、
  同じ引数の `solve` も共有して、画面更新が **17.0ms → 5.9ms**。

**うまくいかなかったこと**
- **検証を、作る側と同じ解き方でしかしていなかった。** そのせいで
  「STEPは4本だけ消す／紙の人は同じ色の8本を消す」というズレが、ずっと素通りしていた。
  18×18で6回作って6回とも壊れていたのに、自動検証は「✓ すべてOK」と言っていた。
- 変数名を付けかえたとき、同じブロックの下に残った参照を見落とした
  （`validateAll` の `results`）。しかも `build()` の広い try/catch がその例外を握りつぶし、
  画面には「この組み合わせでは作れませんでした」としか出なかったので、
  **バグを仕様の限界だと思いこみかけた**。ベンチが全滅して初めて気づいた。
- CSSで `display:flex` が `hidden` 属性に勝つ落とし穴に、**同じセッションで2回**はまった
  （`.toolbar` で直したのに、あとから足した `.draw-help` で同じことをした）。
- 大きい置換スクリプトを1本にまとめたら、途中の1か所が合わずに全体が中止になり、
  書けたつもりの修正が入っていなかった。あとで grep して気づいた。
- セッション終了時の自動記録が、同じ内容を「セッション194」として二重に書き、
  しかも**存在しないテストファイル名・ちがう関数名・ちがう数値**を混ぜていた。

**発見**
- **出力物を人が別の手がかり（色・見た目・言葉）で扱うなら、テストもその手がかりで解き直す。**
  内部の id や key だけで検証すると、「機械は正しいが人には解けない」ものが検証を素通りする。
- **リトライを回す仕組みの中の広い try/catch は、バグを「できませんでした」に化けさせる。**
  捕まえた例外は回数とメッセージを残し、それがいちばん多ければ
  「これは組み合わせの問題ではなく道具の不具合です」と正直に出す。
- **「モードAのときだけ更新する」処理は、モードBで前の値を持ち越す。**
  早期 return は「何もしない」ではなく「前の状態を残す」という意味になる
  （`routePaths` も `routeColor` も、これで持ち越されていた）。
- **同じ意味の値を2か所に持つと、必ず食い違う。** 大きさの上限（入力欄4〜30／生成6〜20）は
  「24×24以上にしてください」と案内しながら20に丸める、という状態を作っていた。
- **番号は体系が2つあるとぶつかる。** ページが1〜5、その中も①〜⑥だったので
  「⑤の①」という言い方になり、どこの話か分からなくなっていた（中身をA〜Fにして解消）。
- **置換スクリプトは1か所ずつ。** まとめて書くと、1つ合わないだけで全部が入らない。

**次回への申し送り**
- **iPad実機テスト待ち（4点）**：④の盤面で指で文字を動かせるか／迷路の大きさが窮屈でないか／
  ツールバーが2行になっても押しやすいか／⑤の見出しがA〜Fで分かりやすいか。
- **自動生成された記録（log.md・task-diary.md）は、コミット前に必ず読んで事実確認する。**
  今回は実際に、存在しないファイル名と誤った数値が書かれていた。
- サブエージェントに点検を任せるときは「編集しない・`grep` で数えて確かめる・
  確認できなかったものは未確認と書く」を必ず指示し、報告は1つずつ再現してから直す。

### 2026-09-07（セッション193・迷路謎メーカー ほんとうの1ページ統合＋生成の行きづまり解消）

**うまくいったこと**
- 「本当に計算上むりなのか、余分な制限が入っているのか」という問いに、
  **推測ではなく計測で答えられた**。生成の `return null` を全部
  `bump('どこで落ちたか')` に置きかえた版をテストから eval して回し、
  「63 trans:erase-wall」→ 直したら「63 place:2」→「28 place:1」と、
  原因が3つ重なっていることを1つずつ見えるようにした。
- 速度も同じやり方で当てられた。関数を `process.hrtime` で包んで
  「solve が 64221回・23.5秒」を先に見つけてから手を入れた（33.3秒→1.3秒）。
- 前回の「1ページ統合」がユーザーの意図と違っていたことを、
  言い訳せずに作り直せた。**上下に並べるのは統合ではない**と気づけたのが要。

**まずかったこと・気づき**
- 前回「1ページに統合した」と報告したが、実際は**上下に並べただけ**だった。
  ユーザーの「そういうことではない！！」で初めて分かった。
  「同じものを2つ持っていないか」（今回は盤面を2つ）を先に探すべきだった。
- CSSの優先順位（型セレクタ > クラス）で、書いたはずの `width` が効いていなかった。
  **書いた値が実際に効いているかを、計算後の値で確かめる**という手が抜けていた。
- 盤面より上にあるタブを、なぞり始めたあとに生やしてしまい、
  ドラッグが1マスで途切れていた。**座標で触るUIの上に置いたものは、
  触れるようになる前に高さを確定させる**。

**セッション後半で足りていなかったこと**
- 「モードAのときだけ更新する」処理を書いたのに、モードBに入るところで
  Aの残した状態を消していなかった（段の答えに前のルートが重なった）。
  **早期 return は「何もしない」ではなく「前の値を持ち越す」**という意味になる。
- 自動生成の失敗を「回数」でしか持っていなかったので、
  使う人に理由を返せなかった。**失敗は場所で覚えておく**と、あとから人の言葉にできる。
- 断り文句を出すより先に、**失敗する前に知らせる**ほうが親切だった
  （入力欄の下に「あと何文字入るか」を常時表示）。断り文句と同じ関数を使えばずれない。

**次に活かすこと**
- 「作れません」と言われたら、まず**どこで落ちているかを数える**。
  原因を1つに決めつけない（3つ重なっていた）。
- 多段の処理で資源（マス・長さ・空き）を配るときは、**必ず最後の段から逆算**する。
  前から「次の1つぶん」を配ると、必ずどこかで足りなくなる。
- 「AとBの全部の組を試す」形を見つけたら、
  **片側で1回だけ計算して、もう片側をふるい分けられないか**を先に考える。

### 2026-09-07（セッション192・迷路謎メーカー 1ページ統合＋2つのバグ修正）

**うまくいったこと**
- 「青い文字が消える」の直し方を、**症状を止める**のではなく**原因を無くす**方向で選べた。
  隠すSTEPを「入れない」だけだと読み取りが壊れるので、そもそも隠す必要が出ないように
  文字の置き方（同じ色の段は前後どちらの道も避ける）を変えた。結果、機能が1つ減って
  仕様も単純になった（紙に印刷したあと文字が動かない、という当たり前の状態になった）
- 画面統合を「作り直し」にせず、**IDと構造を変えずCSSの意味だけ変える**方針にしたので、
  editor.js / app.js の配線を1行も触らずに済んだ。既存のブラウザテスト29本が
  そのまま通ったことが、壊していないことの証拠になった
- まぎれ文字の重複を直したとき、最初のテストが「答えの文字どうしの重複」も一緒に数えていて
  失敗に見えた。テストの数え方を「まぎれ文字がからむ組」に直して切り分けたら、
  実装は正しく、残りは文章に同じ字が入っているだけだと分かった

**うまくいかなかったこと**
- 上記のとおり、最初のテストで「こちらで選べるもの（まぎれ文字）」と
  「選べないもの（答えの文字）」を区別せずに数えてしまい、直っているのに失敗に見えた

**発見**
- 「あとから隠す・あとから消す」で辻褄を合わせている実装は、成果物が紙・画像など
  **あとから動かせないもの**のときは必ず破綻する。実行時に状態を変える解決策が使えるかは、
  出力媒体で決まる（failures.md に記録）
- 画面の統合は、DOMのIDを保てば「表示のしかた（CSS）＋移動のしかた（scroll）」の
  置きかえだけで済むことが多い。先に「何を変えないか」を決めると安全に進む（patterns.md に記録）

**次回への申し送り**

- 統合の続きとして検討できること：4の編集エリアを「よく使う3つ」と「高度な機能」で

### 2026-09-07（セッション191・迷路謎メーカー 段の色・読む順の個別上書き）

**うまくいったこと**
- 「同じ色を繰り返し使っても安全か」を、しかけの種類ごとの**理由**（線けしは道が重なる／
  スタゴルは重ならない）に立ち返って判断したことで、新しいルール（既定は赤に戻す）と
  既存の教訓（2026-09-06「段が増えても勝手に色を変えない」）を両立できた。
  最初は一律「直前と同じ色を避ける」ガードを書いてしまい、テストで矛盾に気づいて直した
- 個別の色上書きを足すと「同じ色の段は必ず連続する」という前提が崩れるため、
  `sameColorRunStart/End`（連続前提）を `sameColorBefore/After`（連続していなくても
  同じ色を拾う）に一般化した。既定の並びでは結果が変わらないことをテストで確認してから
  置き換えたので、リグレッションなく安全に一般化できた
- 回帰テスト（combo3.js）で「スタゴル×2」の成功率が一時的に下がって見えたが、
  コードの計算過程を手で追って旧実装と完全一致することを確認し、原因は
  自分のテストが使った文章が長すぎただけ（短い文章で取り直したら6/6成功）と判明。
  「疑わしきはまずコードを読んで比較」で無駄な修正をせずに済んだ

**うまくいかなかったこと**
- 上記のとおり、最初の実装で「直前と同じ色を避ける」を全しかけに一律適用してしまい、
  一度作り直しになった

  特定してから適用範囲を決めないと、理由が当てはまらない別のケースまで

### 2026-09-06（セッション188・迷路謎メーカー 第10弾つづき：画像に指示文＋スマホ保存）

**うまくいったこと**
- 「大きさを決める（measure）」と「実際に描く（drawBoard）」という、このプロジェクトが
  最初から守っている約束（1つの描画関数にまとめる）を、指示文の折り返し計算にも

  試す形にしたので、「関数がある＝使える」という誤判定（一部のブラウザはshareはあるが
  ファイル共有には非対応）を避けられた

**うまくいかなかったこと**
- 最初の実装は「最小サイズまで縮めれば必ず1行に収まる」という前提で作ってしまい、
  自動作成の指示文（そこそこ長い）を試して初めてはみ出しに気づいた。文章の長さの
  上限を最初に考えず、「縮められるから大丈夫」と思い込んだのが原因

  「記号がふれません」になる。A「さくら」×B「やまと」の組があってこそ「さ＝や」のマスができる

### 2026-09-23 ②（ポケット秘書 第3弾：お金を運賃・ホテル代だけに／設定をアプリが案内・自動化）

**うまくいったこと**
- 「設定が難しい」を、**手順書を分かりやすくする**ではなく**手順そのものを消す**方向で考えた。
  保管庫の作成（wrangler の自動作成）・表づくり（サーバーが初回に作る）・合言葉の登録（画面で決める）・
  講師の方のログイン（招待リンク）と、4つの手作業をそれぞれ別の仕組みで0にできた
- wrangler が本当に保管庫を自動で作るかを、**推測ではなく wrangler の中身を読んで確かめた**
  （名前で探す→無ければ質問なしで作る）。手順書の「うまくいかないとき」にも、その仕組みに沿った逃げ道を書けた
- iPhone の「Safari とホーム画面で保存場所が別」という落とし穴を、**6けたの番号を2か所（アドレス欄と説明書）に
  入れておく**ことで、講師の方が何も入れずに済む形にした。渡らなかったときの手入力の画面も用意した
- テストで**講師の方になりきって**最初から最後まで通した（LINEの招待→Safari→アイコン→通知→テスト通知の復号）

**うまくいかなかったこと**
- **テストが全部通ったのに、スクリーンショットで2つ見た目の不具合が見つかった。**
  済みのカードを `opacity` で薄くしていて「LINEで送る」まで押せないように見えた／
  補足文字のクラスを親の下にしか書いておらず、設定画面では大きく出た。
  コントラストのテストは「計算後の色」しか見ず、opacity を見ていなかった
- 前回決めた「テストの片づけは始めに」が、**宛先の分からない他人の登録**には使えなかった。
  始めに消せないものは「増減で数える」に切りかえた
- テストの期待値にポート番号を直書きしていて、別のサーバーで流したときだけ落ちた

- **「保管庫は自動で作られる」と書いたのは誤りだった見込み。** wrangler の中身は確かめたが、

**発見**
- **「自動でできる」と書く前に、それを実際に動かすのは誰（どの鍵・どの権限）かを確かめる。**
  道具の中身の確認と、本番の権限の確認は別物。手元のテストは権限を使わないので素通りする
- **opacity は色の値を変えない。** 計算後の色で測るテストは素通りする。見た目は必ず目で見る
- **同じ部品を2つ目の場所で使いはじめたら、CSSが親に閉じていないか確かめる**
- 「はじめの準備」のような案内は、**アプリが自分で「済み」を判定できる**と強い
  （ホーム画面から開いている＝追加済み、など）。人に「できましたか？」と聞かなくて済む
- 合言葉を「最初に開いた人が決める」方式は手作業を減らすが、**先に他人が開く**リスクがある。
  手順書に「すぐ開く」と、やり直しのSQL（合言葉・ログイン・通知の宛先を消す）をセットで書いた

### 2026-09-23 ポケット秘書 第2弾 — オンライン秘書アプリ（PWA＋Cloudflare）に作り直し

**うまくいったこと**
- 要件が広がった時点で、**前の設計と両立しないことを先に正直に伝えてから**作り直しに入れた。
  とくに前回 README に書いた「ホーム画面に追加してもSafariタブで開く作りにした」が
  **今回は真逆になる**点を、自分から訂正して説明できた
- 「App Storeの有料アカウントもMacも無い」という条件を**制約ではなく絞り込みとして使った**。
  選択肢を表にして数えたら PWA ひとつしか残らず、技術選定で迷う時間がゼロになった
- OAuth を**使わない**判断。未審査だと7日でトークンが切れ、渡した相手の手元で必ず壊れる。
  代わりに ICS の二方向（購読用URLを配る／シークレットアドレスを取り込む）で実質双方向にした
- 暗号まわり（Web Push）を、**自分で復号し直せる形**に切り出してから書いた。
  さらに Node で偽の通知サーバーを立てて「暗号化 → HTTP送信 → 復号」を1本につなげた。
  ライブラリ無しの実装でも、往復させれば正しさを証明できる
- サーバーと画面で同じファイル（`shared-date.js` / `shared-model.js`）を読む形にした。
  サーバーは世界標準時で動くので、日本時間に直す処理を2か所に書いたら必ずどこかで1日ずれていた
- **オフラインの真っ白を「テスト環境のせい」で片づけなかった。** SWの処理を
  「その場で作った応答を返すだけ」に差しかえる実験をして、
  「ナビゲーションはSWに届いている＝自分の分岐が原因」と確定させてから直した

**うまくいかなかったこと**
- **テストを書く順番を間違えた。** 画面テストを単体でしか流しておらず、
  サーバーテストの後に流したら11件落ちた。前のテストが残したデータを引きずっていた。
  その過程で**本物のバグ**（取り込みをやめたカレンダーの予定が消えない）も見つかったので
  結果的には良かったが、最初から「順番を変えて2回流す」をやっていれば早く気づけた
- 最初に書いたテストの測り方が雑だった。背景が透明な要素のコントラストを
  「黒」と比べて誤判定し、チェックボックスのタップ領域も「包んでいるラベル」ではなく
  入力欄そのもので測っていた。**3件を不具合だと誤って報告しかけた**
- 通知の重複防止が効いて、同じ分内にテストを2回流すと2回目が落ちた。
  仕様どおりの正しい動作なのに、固定IDを使っていたせいで失敗に見えた

**発見**
- **転送された応答（redirected）は、画面をひらく要求には使えない。** `cache.add('/index.html')` は
  サーバーの転送先（`/`）を取ってくるので印が付く。`clone()` では消えない。**応答を作り直す**しかない。
  PWAをオフライン対応させるときの定番の落とし穴
- **「値が変わったときだけ描く」最適化は、初期状態を描かない。** 状態と見た目を合わせる処理に
  条件を付けてはいけない。描画の節約より初期表示の正しさが先
- **設定を換算して当てはめるときは、換算後に同じ値へ潰れないか数える。**
  「1440分前・120分前・30分前」を日数に直すと 1日前・0日前・0日前になり、通知が二重に出た
- **「取り込む」機能を作ったら、必ず「やめたとき」も書く。** 追加と更新だけ考えて削除を忘れると
  画面に幽霊が残る。テストを順番を変えて流したら露見した
- **テストは「どの順番で、何回流しても同じ結果」になるまでが完成。**
  片づけは終わりではなく**始めに**書く（途中で落ちても次が動くため）
- iPhone の Web通知は **iOS 16.4以降＋ホーム画面に追加したアイコンから起動**が必須条件。
  Safariのタブのままでは許可のボタンすら押せない。ここを画面で案内しないと渡した相手が必ず詰まる

**次回への申し送り**

  私はアカウントを作れないため未実施。**手順書の画面文言は私が実地で確かめたものではない**ので、
  「書いてあるボタンが無い」ときは止めて聞いてもらう（自己流で進めるより早い）

  ③電話・地図のタップ ④縦持ちの見やすさ

- **数値テストとスクリーンショットは役割が違う。** 前者は「幅は足りているか」しか見ないので、
  文字が切れていても重なっていても通る。**人が見るものは、最後に人と同じ見方で確かめる**
- 端末内保存のツールは、書き出し口を**ファイルと文字コピーの2経路**用意しておくと事故らない

### 2026-09-12（②）ことばかける君 index.html — キーワード自動検索の候補数不足・毎回同じ結果になる不具合を修正

**うまくいったこと**
- 伊神さんの報告「候補が2件しか出ない・毎回同じにしてほしい」を受けて2点を修正
  - `findKeywordCandidates` が辞書を頻度順のまま先頭から調べていたため、
    毎回まったく同じ語が同じ順で見つかっていた（決定的で変化がなかった）。
    「文字がそろっている語」を先に軽く集めてから**シャッフルしてから**
    `pickMarkCells` の重い判定にかけるようにし、毎回ちがう候補が出るようにした
  - `autoFindKeyword` 側の1文字数あたりの上限（2件）・全体の目標（8件）が低すぎた。
    試す文字数の幅を ±2→±3 に広げ、1文字数あたり6件・全体目標16件に引き上げた
- 実際に7語登録・6語盤面の状態で3回連続検索し、毎回12件・内容が違うことを確認
- 3語登録・2語盤面という小さい盤面でも11件・32msで見つかることを確認（性能も問題なし）

**発見**
- 「候補をさがす」機能で辞書を先頭から順に調べるだけだと、**呼ぶたびに同じ結果**になる。
  「毎回ちがう」を実現するには、重い判定（ここでは `pickMarkCells`）にかける前の
  軽い候補集めの段階でシャッフルすると、判定の回数を増やさずに多様性が出せる

**次回への申し送り**

### 2026-09-12（ことばかける君 index.html「新しく作る」の動作確認・キーワード自動検索を新規実装）

**うまくいったこと**
- 「①新しく作るが機能していない」という報告を受け、`newWork`/`confirmDiscard`/`saveAsWork` の
  実装を読み、さらに Playwright で実際の画面操作（タブ切り替え→未保存の変更を作る→
  「新しく作る」クリック→「保存してから進む」→「上書き保存する」）を再現。
  結果、**「保存する／保存せず消す／やめる」→（保存を選び、既存作品なら）
  「上書き保存／別の作品として保存／やめる」の2段階ダイアログは実装どおり正しく動作し、
  完了後は state.workId・タイトル・登録語・盤面がすべて正しく空に戻ることを確認**
- 「②登録ワードからキーワードを自動でさがすボタン」を新規実装。
  ③しあげの「キーワードの記号」パネルに追加し、盤面にある文字だけで作れる・
  辞書にある言葉になる候補を検索してタップで確定できるようにした
  - 記号を実際にふれるかの判定は、既存の `pickMarkCells`（1語からの取りすぎ防止・
    登録ワード優先・いろんな語に分散）をそのまま再利用し、二重の実装を避けた
  - ねらう文字数は「登録ワード数 ±2文字」を中心に複数の長さを試し、
    見つかった候補の文字数がバラけるようにした
  - 盤面にそのまま出ている語は候補から除外（答えが丸見えになるのを防止）
- 実際にビルドしてボタンを押すテストを複数パターン（登録語2〜7語）で実行し、
  候補が出るケース・「見つかりませんでした」と正しく案内されるケースの両方を確認

**うまくいかなかったこと**
- 「新しく作るが機能していない」の具体的な再現には至らなかった（コードとテスト双方で
  正しい動作を確認したため、実装のバグとしては特定できていない）

**発見**
- ★のときと同様、「体感で聞いた不具合」は必ず実際に手を動かして再現を試みてから対応する。
  再現できなければ「バグでした」と決めつけず、正直に「見つかりませんでした」と伝えて
  具体的な状況を聞く方が、見当違いの修正をするより早い
- 新しい自動検索機能は、既存の `pickMarkCells` の制約ロジックをそのまま流用することで、
  「記号は実際にふれるが表示上の判定だけ通っている」という不一致を防げた

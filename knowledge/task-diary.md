### 2026-05-31（GitHub Actions ワークフロー実行エラーのデバッグ方法説明）

**うまくいったこと**
- GitHub Actions ワークフロー実行でエラー（exit code 1）が発生した際の診断方法を体系化して説明
- 「exit code だけでは原因不明」→「ログを見る3ステップ」を明確に提示
- Artifacts（スクリーンショット）から停止位置を視覚的に特定する方法を説明
- ありがちなエラーパターン一覧表（クッキー関連・ファイルパス・ライブラリ・Playwright）を提供

**うまくいかなかったこと**
- 実際のログ本文またはスクリーンショットをユーザーがまだ確認していないため、原因の確定には至らず

**発見**
- ワークフロー実行エラーの診断には「ログの詳細確認」「Artifacts のダウンロード」「画像による視覚確認」の3つのステップが必須
- GitHub Actions UI では「❌ がついてるステップをクリック」することで、そのステップのログが展開される仕組み
- exit code 1 だけでは原因の 99%は特定不可。必ず「ERROR:」「Traceback」「WARNING:」などのキーワードを探す必要がある

**次回への申し送り**
- ユーザーが次セッションで以下を確認予定：
  1. 失敗したワークフロー実行ページで❌ステップのログを展開・読む
  2. Artifacts（note-post-screenshots 等）をダウンロード・確認
  3. スクショでどのUI要素で止まっているかを確認
- ログ本文またはスクショを提供してもらえれば即修正可能

### 2026-05-31（note.com クッキー取得フロー説明と技術制約の明確化）

**うまくいったこと**
- note.com のクッキー取得が「本人（ユーザー）操作が必須」であることを3つの理由で明確に説明
  - ① クラウド実行環境からブラウザアクセス不可
  - ② データセンター IP は bot 判定される（reCAPTCHA直撃）
  - ③ パスワード共有はセキュリティ上避けるべき設計
- ユーザーが既にブラウザでログイン済みの状態を活用する戦略を提示

**うまくいかなかったこと**

- Playwright bot 検知回避と別の問題層（IP・ブラウザセッション）が存在することが判明

**発見**
- Playwright の stealth 対策は navigator / chrome / webgl の偽装に有効だが、IP ベースのブロックには無力
- note.com の最終的なクッキー検証ロジックはサーバー側で秘匿されている
- データセンター IP での自動クッキー取得は、reCAPTCHA 対策技術の進展如何に関わらず、根本的に限界がある

**次回への申し送り**
- ユーザーが実施中：ブラウザで Cookie-Editor → JSON 出力 → Secrets 登録
- AI がサポートできる範囲：画面スクショ → 何をすればいいか指示、エラーメッセージ → 原因特定
- 「代わりに操作する」ではなく「横で指示する係」として機能することがこのタスクの現実的な分担

### 2026-05-31（Playwrightクッキー認証の実装検証と修正）

**うまくいったこと**
- Playwrightをインストールして実際に型定義を確認
- Cookie-Editorの出力形式とPlaywright `SetCookieParam` の非互換性を特定（sameSite、expirationDate）
- `normalize_cookies()` 関数を実装・テスト完了、単体テストで正常動作確認
- normalize_cookies()の出力が全フィールド準拠であることを検証
- 両モジュール（post_to_note.py、post_to_booth.py）での統合テスト完了

**うまくいかなかったこと**
- Chromiumのダウンロードがネットワーク制限で不可（環境制約）
- 前回実装したコードが重大な型エラーを含んでいた（ユーザーが貼ったクッキーは認証スキップされていた可能性）

**発見**
- Cookie-Editorの形式とPlaywright要件の非互換性：
  - Cookie-Editor: `"sameSite": "lax"` → Playwright: `"Lax"` (大文字必須)
  - Cookie-Editor: `"expirationDate": 1764000000` → Playwright: `"expires"` フィールド（異なるキー）
- 前回のコードではこの変換がなく、ユーザーがクッキー認証を試しても失敗していた可能性
- Playwright公式の `SetCookieParam` 型定義を直接inspectして検証することの有効性

**次回への申し送り**
- ブラウザ自体は環境制約でローカル実機テスト不可
- GitHub Actions上での実運用動作確認が必須（ユーザーがワークフロー再ラン → ログ確認）
- ログに `🍪 クッキー認証 (N個・正規化済み)` と `✅ クッキーログインOK` が出れば成功
- 今度のコードは Playwright公式型定義とCookie-Editorのマッピング検証済みで信頼度が高い

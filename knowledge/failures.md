# 失敗・ハマりポイント集

## 「文字の無い区間」を探したら、1つも無かった（前提を数えずに実装した）

**症状：** 「ルートを遠回りにする」機能で、
「文字が置かれていない区間を選んで、そこを迂回路に置きかえる」実装をしたら、
**300回試して300回とも「区間に文字がある」で失敗**した。

**原因：** その迷路では、**ルートの上は全マスに文字が置かれていた**。
まぎらわしさを出すために、道の空きマスをすべて埋める処理（`fillGaps(..., ratio: 1)`）を
自分で入れていたのに、それを忘れて「文字の無い区間があるはず」と思いこんでいた。

**対処：** 前提を変える。**文字を避けるのではなく、文字を連れていく。**

```js
// 区間にある文字を集めて、迂回路の上へ順番どおりに置きなおす
const moving = collectElementsOn(route.slice(i+1, j));
moving.forEach((group, m) => group.forEach(e => { e.r = spots[m].r; e.c = spots[m].c; }));
```

**教訓：** 「〇〇が無いマス」を探す実装を書く前に、**そのマスが実際にいくつあるかを数える**。
数えるコードは3行で書ける。300回の失敗を見てから調べるより、はるかに速い。

**タグ：** #前提の確認 #デバッグ #meiro-nazo-maker

## 「消した壁」をもう一度消そうとしていた（2段目以降で何も起きない）

**症状：** 「線を消す」段を2回重ねたとき、2段めで道がまったく変わらないことがあった。

**原因：** 近道になる壁をさがす関数が `if (!walls[key]) return;`（壁が無ければ飛ばす）
としか書いていなかった。**1段めで「消した」壁は `disabled = true` になるだけで辞書には残る**ので、
候補に入ってしまい、もう一度消しても何も起きなかった。

```js
// ✗ 壁が「ある」だけを見ていた
if (!walls[key]) return;
// ○ すでに消してあるものも除く
if (!walls[key] || walls[key].disabled) return;
```

**教訓：** 「消す」を3種類（見た目だけ／無効にする／完全に消す）で持っている設計では、
**「ある」の判定に必ず状態も入れる**。`walls[key]` の存在チェックだけでは足りない。

**タグ：** #状態管理 #論理削除 #meiro-nazo-maker

## 迷路の答えに「行って戻る」が混ざっていた（交差はいいが、なぞり返しはダメ）

**言われたこと：** 「絶対条件として、同じ道は通らないを追加。交差はいいが、なぞるのはダメ。」

「○を全部通る」謎で、探索が返す道が **同じ通路を行って戻る歩き方**になっていた。
盤面を見ても道が1本重なって見えるだけで、解く人には「どっちに進むのか」が分からない。

**見分け方：マスではなく「マスとマスのあいだ」で数える。**

```js
function retracedEdges(path) {
  const used = {}, out = [];
  for (let i = 0; i + 1 < path.length; i++) {
    const key = edgeBetween(path[i], path[i+1]);   // 通路（辺）をキーにする
    if (used[key]) out.push(key);
    used[key] = true;
  }
  return out;
}
```

- **交差** … 同じ*マス*を2回通る。ただし通路は別（縦に通ったあと横に通る）→ **OK**
- **なぞり返し** … 同じ*通路*を2回通る → **NG**

マスで数えると交差まで弾いてしまい、○を通る謎が作れなくなる。**辺で数えるのが正解。**

**あわせて分かったこと：** 自分で描く正解ルートは、**交差させると最短にできない**。
交差点では角を切って近道できてしまうため。だから交差を使いたいときは
「○を全部通る」のようなしかけと組み合わせる必要がある。これは断り文句として画面に出すようにした。

**タグ：** #迷路 #経路 #交差 #謎解き #meiro-nazo-maker

## 例文が「前の組み合わせのまま」残って、意味の合わない初期値になっていた

**症状：** かんたん作成で、しかけを選び直しても文章欄の例文が変わらない。
1段の謎で「なぞがとけた」と入っていた欄が、2段の謎にしても「なぞがとけた」のままで、
1段めの指示欄に「なぞがとけた」という意味の通らない例文が入っていた。

**原因：** 欄の値を `W.texts[key]` に覚えていて、
「使う人が書きかえた値」と「こちらが入れた例文」を区別していなかった。
値があれば必ずそれを使うので、例文を入れ直す機会が無かった。

**対処：書きかえたかどうかを別に持つ。**

```js
const W = { texts: {}, edited: {} };
ip.value = W.edited[key] ? (W.texts[key] || def) : def;   // 書きかえていない欄は例文を入れ直す
ip.addEventListener('input', () => { W.texts[key] = ip.value; W.edited[key] = true; });
```

**教訓：** 初期値を出す欄では、**「まだ触っていない」状態を明示的に持つ**。
値の有無で判断すると、状況が変わったときに古い初期値が残る。

**タグ：** #UI #フォーム #初期値 #meiro-nazo-maker

## 「ぜんぶ入っている道具」は、入口が1つに決まっていないと使われない

**言われたこと（迷路謎メーカー第1弾）：**

> ステップも設定もやることが多すぎる。何から、どれを、やればいいかわからん！！

機能は全部あった。検証も通っていた。それでも使えなかった。
理由は「**最初に何を押せばいいか**」が画面のどこにも書かれていなかったから。
左にSTEP一覧、中央にキャンバス、右に8個の折りたたみパネル。全部が同じ強さで並んでいた。

**対処：入口を1つだけにする。**

```
【前】 開くといきなり編集画面（ツール11個・パネル8枚・STEP一覧）
【後】 開くと「かんたん作成」だけ
       ① どんな謎にするか カードで選ぶ
       ② こたえになる文章を入れる
       ③ 「自動で作る」を押す → 印刷
       編集画面は「✏️ くわしく直す」の奥に置く（いつでも「🏠 かんたん作成」で戻れる）
```

**やったこと**
- 画面を3段に区切り、番号（①②③）を丸で振った
- ②③は、①を選ぶまで薄く表示（`opacity:.45`）して「まだここじゃない」と分かるようにした
- 細かい設定（大きさ・文字の量・START位置）は `<details>` に畳んで「ふつうはそのままでOK」と書いた
- 迷った項目そのものを消した：「消し方3種類（無効／見た目だけ／完全）」は、
  印刷して解く用途では区別する場面が無かったので**選択肢ごと撤去**した

**教訓：** 機能を足すほど「何からやればいいか」は分からなくなる。
**足したら、入口を1つに絞り直す**までがセット。
「使う人が迷う選択肢」は、説明を足すのではなく**消せないか**を先に考える。

**タグ：** #UI #情報設計 #入口 #機能過多 #meiro-nazo-maker

## 同じ「もどす」でも、対象が2つあるとユーザーは押せなくなる

**言われたこと：**

> ステップの設定も一つ戻すボタンが欲しい（ステップなのか迷路なのかどちらを戻すなのか混乱させないように）

「もどす」ボタンが1つしかないと、押した人は
「これは迷路が戻るのか、STEPが戻るのか」が分からず、**こわくて押せない**。

**対処：履歴を2本に分け、ボタンの名前に対象を書く。**

```js
// 迷路の履歴（editor が持つ・Ctrl+Z）
ED.pushHistory();        // 壁・文字・START/GOALを変える前
// STEPの履歴（app が持つ・別ボタン）
pushStepHistory();       // STEPの追加・削除・並べかえ・設定変更の前
```

ボタンの名前も「↶ もどす」→「**↶ 迷路をもどす**」「**↶ STEPをもどす**」に変えた。
テストでも「STEPをもどしても迷路は変わらない」を明示的に確かめている。

**教訓：** Undo は「何が戻るか」が言えないと機能しない。
対象が2つ以上あるなら、**履歴もボタンも分ける**。1つにまとめて説明で補うのは失敗する。

**タグ：** #UI #Undo #meiro-nazo-maker

## 「動かす」ツールが、動かしたいものと違うものを動かしていた

**言われたこと：** 「動かすは、記号や文字を動かしたいの、迷路全体は動かさない」

ツールバーに「✋ うごかす」を置いたが、これは**画面（キャンバス）を動かす**ものだった。
使う人が「動かす」で連想するのは**置いた文字や記号**のほう。名前が期待と逆を向いていた。

**対処：ツールごと消した。**
- 文字・記号を動かす → 「えらぶ」でドラッグ（もともとできた）
- 画面を動かす → 指2本、または**盤（白い紙）の外側をドラッグ**

```js
function outsideBoard(e) {           // 盤の外をつかんだら画面を動かす
  const m = R.measure(shownBoard(), baseOpts());
  const p = boardPoint(e);
  const slack = m.cell * 0.35;
  return p.x < m.pad - slack || p.y < m.originY - slack ||
         p.x > m.pad + b.cols * m.cell + slack || p.y > m.originY + b.rows * m.cell + slack;
}
```

**教訓：** 道具の名前は「その道具が何をするか」ではなく
**「使う人がその言葉で何を思い浮かべるか」**で決める。
ずれていたら、名前を直すより**その道具が要るのかを疑う**ほうが早い。

**タグ：** #UI #命名 #meiro-nazo-maker

## ピンチ拡大の1本目の指で、道具が動いてしまう（iPad）

**症状：** iPadで2本指の拡大をしようとすると、描いていた正解ルートが途中で切れる。
壁ツールのときは壁が消える。マウスでは絶対に再現しない。

**原因：** 2本指でも、指は必ず**1本ずつ**触れる。1本目の `pointerdown` の時点では
「これはピンチの始まりだ」と分からないので、ふつうに道具の処理が走ってしまう。
2本目が来て初めてピンチだと分かるが、そのときには1本目の変更が済んでいる。

**対処：** 2本目のポインタが来たら、**1本目でした変更を取り消す**。
Undo用の履歴を使えば数行で書ける。

```js
function onPointerDown(e) {
  ...
  if (pointerCount === 2) { cancelPendingEdit(); startPinch(); return; }
  S.histLenBefore = S.history.length;   // ここから先の変更は取り消せるように印をつける
  startTool(e);
}
function cancelPendingEdit() {
  let snap = null;
  while (S.history.length > S.histLenBefore) snap = S.history.pop();
  if (snap) restore(JSON.parse(snap));   // いちばん古い＝1本目が触れる前の状態にもどす
}
```

**教訓：** タッチ対応は「2本目が来るまで1本目の意図は確定しない」。
マウスでのテストだけでは絶対に見つからないので、**CDPの `Input.dispatchTouchEvent` で
2点タッチまで自動テストする**こと。

**タグ：** #iPad #タッチ #ピンチ #pointerevents #meiro-nazo-maker

## 白黒印刷で色を「線のもよう」で分けるとき、丸い線のはしがすきまを埋める

**症状：** 印刷で色が使えないぶん、壁の色を破線・点線に置きかえたのに、
**どの色の壁も同じ実線に見える**。

**原因：** `ctx.lineCap = 'round'` を付けたまま `setLineDash()` していた。
丸いはしは線の太さの半分だけ両側にはみ出すので、線が太い（7px）のに
すきまが狭い（5px）と、はみ出した分が**すきまを完全に埋めてしまう**。

**対処：** 破線にするときは `lineCap = 'butt'` にする。

```js
if (mono && color !== 'black') {
  ctx.lineCap = 'butt';           // round のままだと破線が実線に見える
  ctx.setLineDash(dashPattern);
}
```

**あわせて：** 白黒では文字にも飾り（下線・丸囲み・四角囲み）を付け、
**凡例に「線のサンプル」と「文字のサンプル」を両方載せる**と、印刷したものだけで意味が通る。

**教訓：** 白黒対応は「色を消す」だけでは足りない。実際に画像を書き出して**目で見て確認**する。

**タグ：** #印刷 #白黒 #canvas #setLineDash #meiro-nazo-maker
## 面をまたいだ語の使い回し：「代入先の面」を逆にするとバグる（dual.html `pickPairPool`）

**症状：** ことばかける君 dual.html で、辞書から足す語をできるだけ共通ワード（A・B両方に同じ語）に
する機能を作ったとき、「B で既に使った語を今回は A の語として使い回す」という実装をしたのに、
毎回 100% 空振りし、候補が 0 のままだった。

**原因（1回目の誤り）：** 「使った語を、もう一度その面の代入先に入れてしまった」。
```js
// ✗ 間違い：Bで使った語を、また db（Bの候補）に代入してしまう
const rt = [...usedB][0];
db = { text: rt, ... };
// 直後の重複チェック usedB.has(db.text) に必ず引っかかり、毎回 continue で捨てられる
if (usedA.has(da.text) || usedB.has(db.text)) continue;
```
「B で使った語」は、次は **A の候補（da）** に代入しないといけない。反対の面に入れて初めて、
直後の重複チェック（`usedA.has(da.text)`）を通過できる。

**実際の直し方（dual.html `pickPairPool` 内）：**
```js
const reuseFromB = [...usedB].filter(t2 => chars(t2).length === n);
const reuseFromA = [...usedA].filter(t2 => chars(t2).length === n);
if (reuseFromB.length && roll < 0.5) {
  const rt = reuseFromB[Math.floor(Math.random() * reuseFromB.length)];
  da = { text: rt, meta: metaOf(rt, n), rank: da.rank };   // ← Bで使った語を A の候補に
} else if (reuseFromA.length && roll < 0.8) {
  const rt = reuseFromA[Math.floor(Math.random() * reuseFromA.length)];
  db = { text: rt, meta: metaOf(rt, n), rank: da.rank };   // ← Aで使った語を B の候補に
}
```

**検出方法：** テストで「各パターン 10+ 回実行」して候補の出現率を計測すると、
デタラメな実装は共通語の出現率が 0% のまま変わらないことですぐ気づける。

**再発防止：**
1. 面をまたぐ再利用ロジックでは、「どちらの面で使った語か」と「代入先はどちらの面か」を逆にする
2. 直後の重複チェック（`usedA.has/usedB.has`）が何を防ぐためのものかを先に確認してから代入する

**タグ：** #dual.html #共通語 #面・マッピング #重複チェック

## 複数単位での数え間違い：「語の文字数」と「マス数」を混同すると判定が狂う

**症状：** ことばかける君で、ユーザーにタップして語を盤面に配置させると、
「キーワードがすべて入りました ✓」という表示が出るのに、実は記号（A・B・C…）が不足していて、
その記号の数を数えると「足りない」という矛盾が生じた。

**原因：** キーワード「せんせい」に含まれる「せ」が**2回**出てくるとき、
「置いた語の中に『せ』という文字が2つ入っている」と数えていた。
しかし実際には、「『せ』を置く**マス**が2つ必要」であり、
2つの語が「せ」の位置で**交差**した場合は、
盤面には「記号がふれるマス」が1つしかない。

つまり **「語に含まれた文字」と「盤面のマス」は単位が違う**のに、
同じように数えていた。

```
盤面：
    A   B   C   D
  ┌───┬───┬───┬───┐
  │ せ│ん │せ │ い│  ← 「せんせい」（「せ」が2マス）
  ├─┬─┼───┼─┬─┼───┤
  │あ│  │ せ│  │ │    ← 「あせ」（「せ」が1マス・交差）
  └─┴─┴───┴─┴─┴───┘

「せ」の数え方の間違い：
  ✗ 語に含まれた「せ」の文字数 = 3個（「せんせい」2個 + 「あせ」1個）
  ✓ 実際に盤面に要る「せ」のマス数 = 3個（「せんせい」2マス + 「あせ」1マス）
    → 文字数では正しく見えるが…

交差が起きた場合：
  ✗ 「置いた語の『せ』」で数えると 3個のままに見える（ウソ）
  ✓ 実際には「記号がふれるマス」は、A・B・C の3つ = 記号が3つ必要（本当）
    → 「記号が4つふれている」なら、実際には記号が**足りない**
```

**対処：** 
1. **「何を単位に数えるか」を明確にする** — 「語の文字」ではなく「盤面のマス」を数える
2. **交差マスは1回だけ数える** — 複数の語が同じマスにふれても、記号は1つ
3. **単位の検証を厳格に行う** — 「表示」と「実算」で矛盾がないか毎回確認
4. **優先度を明示する** — 「キーワード完全 > 語の数 > マスの効率」の順で優先する設計

**再発防止：** 
- 複数の「単位系」が登場する計算では、**各ステップで単位を明記する**
  ```js
  // ✗ だめ
  const count = wordLetters.length;
  
  // ✓ いい
  const gridCellsNeeded = new Set();  // マス単位で数える
  for (const word of words) {
    for (const cell of word.cells) {
      gridCellsNeeded.add(cell.id);   // 交差は自動でユニーク化
    }
  }
  const symbolCount = gridCellsNeeded.size;  // 「マス数」として明記
  ```

**「うそをついていた」ことが最悪だった点：**
- ユーザーの判断を誤らせる（「入った」と思わせるのに実は入っていない）
- 問題の原因特定を遠ざける（「システムが言ってるので大丈夫」→ 実は違う）
- 次のセッションでの同じ問題を再現させてしまう可能性

**タグ：** #単位混同 #交差判定 #数え方 #透明性 #crossword #セッション159

## 画面用と印刷用でマスを別々に描いていると、片方だけ要素が抜ける

**症状：** ことばかける君で、画面の盤面や解答モードには番号（1・2・3…）が出るのに、
**印刷したものだけ番号が無い**。カギ一覧は「1. ○○」と番号で指しているので、問題として解けない。

**原因：** 画面用 `renderGrid()` と印刷用 `buildPrint()` でマスの描画コードが別々にあり、
印刷側だけ「番号」を描いていなかった。記号（A・B・C…）・色・罫線は両方にあったため気づきにくかった。

**対処：** 印刷側にも番号を足し、**位置の約束も画面とそろえる**（記号＝左上／番号＝右上）。

**再発防止：** 同じものを2か所で描いている箇所は、**片方に要素を足したらもう片方も確認する**。
確認は「画面に出るか」だけでなく、**印刷プレビュー（またはbuildPrintの出力）まで見る**こと。
このツールでは次の4か所が同じ盤面を描いている：
`renderGrid()`（画面）／`buildPrint()`（印刷）／`solveRender()`（解答モード）／`skelPreview`（プレビュー）

## ダブルタップ抑止：「2度目を無視する」実装は連続タップまで潰す（危険）

**症状：** ダブルタップ（拡大）を防ぐため、2度目のタップを無効にする handler を書いたら、連続入力（`あんぱんまん`など6字タップ）ができなくなった。

**原因：** よく見かける実装：
```js
let touchCount = 0;
document.addEventListener('touchend', (e) => {
  touchCount++;
  if (touchCount === 2) {
    e.preventDefault();      // ← 2度目を無視する
    touchCount = 0;
  }
}, false);
```
これは「素早い2つのタップを同じ位置にされたら無視」という意図なのに、実装が雑だと**3度目のタップまで無視**されてしまう。または callback の timing ずれで、連続した単純なタップ（異なる位置、目的が違う）まで検出されてしまう。

**対処：** CSS-only ソリューションを使う（JavaScript handler は不要）：
```html
<!-- meta viewport -->
<meta name="viewport" content="width=device-width, initial-scale=1, user-scalable=no">
```

## 外部APIの「Failed to fetch」は、ネット不通ではなくCORS非対応を疑う

**症状：** ブラウザから `fetch()` で外部APIを呼ぶと `Failed to fetch` になる。
ユーザーは「ネットには間違いなくつながっている」と言う。実際つながっている。

**原因：** 呼び出し先が **CORS（Cross-Origin Resource Sharing）に対応していない**。
別サイトのデータ取得はブラウザ側が安全のため遮断するので、通信自体が成立しない。
`Failed to fetch` はネットワーク不通と区別がつかないメッセージなので誤診しやすい。

**見分け方：** そのAPIのドキュメントに **`callback` パラメータ（JSONP）がある**なら、
CORS非対応の可能性が高い。JSONPはCORSが無い時代の回避策なので、
「わざわざJSONPを用意している＝CORSで取れない」という裏付けになる。

**対処：** `<script>` タグでの読み込み（JSONP）に切り替える。
`<script>` の読み込みはCORSの対象外なので通る。

```js
function jsonpRequest(url, timeoutMs) {
  return new Promise((resolve, reject) => {
    const cbName = 'cb' + Date.now() + Math.floor(Math.random() * 10000);
    const script = document.createElement('script');
    let finished = false;
    const cleanup = () => {           // ← 後片付けを必ず行う
      clearTimeout(timer);
      if (script.parentNode) script.parentNode.removeChild(script);
      try { delete window[cbName]; } catch (e) { window[cbName] = undefined; }
    };
    const timer = setTimeout(() => {  // ← 応答が来ない場合に備えて必須
      if (finished) return; finished = true; cleanup();
      reject(new Error('応答がありません（時間切れ）'));
    }, timeoutMs || 15000);
    window[cbName] = (data) => { if (finished) return; finished = true; cleanup(); resolve(data); };
    script.onerror = () => { if (finished) return; finished = true; cleanup(); reject(new Error('つながりません')); };
    script.src = url + '&callback=' + cbName;
    document.body.appendChild(script);
  });
}
```

**注意点：**
- JSONPは応答が来なくても `onerror` が発火しないことがあるので、**タイムアウトは必須**
- コールバック名は毎回ユニークにし、成功・失敗どちらでも `window` から削除する（グローバル汚染防止）
- JSONPは外部のJSをそのまま実行する方式なので、**信頼できる相手にだけ**使う

**エラー文言の教訓：** 「ネットにつながっていない可能性があります」と書いたせいで、
ユーザーを混乱させた。外部サービス連携の失敗メッセージは
**「サービス側につながらないだけで、ネットの不調とは限りません」**と書くべき。

**タグ：** #CORS #JSONP #fetch #外部API #エラーメッセージ

### [2026-08-22] crossword — 日本語入力（IME）の変換中の文字が1マスずつ確定されてしまう

**症状：** 配布リンクの解答モードで、PCで「た」と打つと1マス目に「t」、2マス目に「た」が入る。
スマホでは同じ文字が繰り返し入る。

**原因：** 1マス1文字の入力欄で `input` イベントを見て即座に確定していた。
日本語入力は**変換中にも `input` が発火する**ため、ローマ字の途中（t）や予測変換の途中（こ→こく→こくご）が
そのまま確定されてしまう。`maxlength="1"` も変換の文字数を制限してじゃまをしていた。

**対応：**
```js
let composing = false;
si.addEventListener('compositionstart',  () => { composing = true; });
si.addEventListener('compositionupdate', () => { composing = true; });
si.addEventListener('compositionend', (e) => {
  composing = false;
  commitText(e.data || si.value);   // 変換が終わった文字だけを確定する
  si.value = '';
});
si.addEventListener('input', (e) => {
  if (composing || e.isComposing) return;   // 変換中は何もしない
  commitText(si.value); si.value = '';
});
```
- `maxlength="1"` は**外す**（変換のじゃまになる）。文字数は自分で扱う
- 確定が2文字以上（「たけ」）なら、続けて次のマスに入れる → かえって入力が速くなる
- 次のマスが無ければ残りは捨てる（最後のマスを上書きしないため）

**教訓：** 日本語を1文字ずつ受け取るUIは、必ず `compositionstart` / `compositionend` で
変換中を除外する。`input` だけを見ていると、日本語環境でのみ壊れる。

## ブラウザUI・入力

### [2026-08-21] crossword-supporter — pointerdown 内の focus() はブラウザに打ち消される

**症状：** マスをタップしたら記号入力欄（重ねた `<input>`）にフォーカスを当てる実装で、`pointerdown` の中で `input.focus()` を呼んでいるのに、**キー入力がどこにも入らない**（ヘッドレステストでも `state.marks` が空のまま）。

**原因：** `pointerdown` の直後にブラウザが互換の `mousedown` を発火し、その**既定動作がフォーカスを移動させる**（クリックした要素／body へ）。自分で当てたフォーカスがその後に奪われる。

**解決策：** `pointerdown` で `e.preventDefault()` してから `focus()` する。
```js
grid.addEventListener('pointerdown', (e) => {
  e.preventDefault();   // これがないと直後にフォーカスを奪われる
  openMarkInput(r, c);  // 中で input.focus()
});
```

**別解：** `setTimeout(() => input.focus(), 0)` でフォーカス処理を後ろにずらす。ただし preventDefault のほうが確実。

**教訓：** 「重ねた input にフォーカスを当てる」系は、**必ず実際にキー入力まで通して検証する**。focus() が呼ばれたことだけを確認しても動作確認にならない。

```yaml
jobs:

      issues: write     # Issue 作成用（これが必須）
    steps:
      - uses: actions/checkout@v3
      - name: Post to X and create issue
        run: python scripts/post_to_x.py
```

```python
    headless=True,
    args=[
        '--disable-dev-shm-usage',
        '--no-first-run',
        '--no-default-browser-check'
    ]
)

context = await browser.new_context(
    user_agent='Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36'
)

# ページ開く前に偽装スクリプトを注入
await page.add_init_script("""
  Object.defineProperty(navigator, 'webdriver', {
    get: () => undefined,
  });
```

### [2026-05-23] 共通 — localStorageはプライベートモードで動作しない

**状況：** スコアや進捗を `localStorage` に保存する実装をした

**問題：** プライベート（シークレット）ブラウジングモードでエラーが発生し、ゲームが動かなくなる

**原因：** プライベートモードでは `localStorage` へのアクセスが制限・禁止される場合がある

**解決策：**

```javascript
// localStorage使用前にtry-catchで保護する
function saveData(key, value) {

    localStorage.setItem(key, JSON.stringify(value));
  } catch (e) {
    // プライベートモードや容量超過の場合は無視して続行
    console.warn('保存できませんでした:', e);
  }
}

function loadData(key, defaultValue) {
  try {
    const item = localStorage.getItem(key);
    return item ? JSON.parse(item) : defaultValue;
  } catch (e) {
    return defaultValue;
  }
}
```

**再発防止：** `localStorage` を使う場合は必ず try-catch で囲む

## 2026-08-28 activeElement ガードでボタンの再描画まで止まった

**症状**：マイ辞書の「消す」を押してもデータは消えるのに、一覧の行が消えない。

**原因**：入力中の再描画を防ぐために
`if (box.contains(document.activeElement)) return;` と書いた。
ボタンをクリックすると**そのボタン自身が activeElement になる**ため、
削除後の `renderMyDict()` が毎回この行で止まっていた。

**対策**：守りたいのは「文字入力の中断」だけなので、INPUT に限定する。

```js
const act = document.activeElement;
if (act && act.tagName === 'INPUT' && box.contains(act)) return;
```

**教訓**：`contains(document.activeElement)` は「入力中か」ではなく
「その中の何かにフォーカスがあるか」。ボタンもフォーカスを取る。

## 2026-08-28 保存しなおすと作品が増えていった（開いている作品のIDを保存し忘れ）

**症状**：ページを開きなおしたあとに「保存」を押すと、
「上書き／別の作品として」を聞かれずに、同じ作品がもう1つ増えてしまう。

**原因**：2つあった。
1. 自動保存のデータ（`serialize()`）に「いまどの作品を開いているか」（`workId`）が入っていなかったため、
   ページを開きなおすと `workId = null`＝「まだ一度も保存していない作品」に見えていた。
2. `workId` を保存対象に入れたあとも、作品を保存した直後に `saveLocal()` を呼んでいなかったので、
   自動保存側の `workId` は `null` のままだった。

**対策**：`serialize()` に `workId` を入れ、`storeWork()` の保存成功時（上書き・新規の両方）に
`saveLocal()` を呼ぶ。「変更があるか」の判定 `workSignature()` からは `workId` を外す
（作品の中身ではないため、IDの変化で「未保存」と誤判定しないように）。

**教訓**：「いま何を開いているか」という状態も、中身と一緒に自動保存する。
保存処理でIDが変わったら、その場でもう一度自動保存する。

## 2026-08-30 キーワードの同じ文字が、交差の1マスに重なって足りなくなった

**症状**：キーワード「せんせい」のように同じ文字が2回あるとき、
盤面に「せ」を含む語が2つあるのに、記号（A・B・C…）が3つしかふれない。
しかも画面には「キーワードの文字もすべて入りました」と出る（うそをついていた）。

**原因**：そろっているかの判定を、**置いた語の文字**で数えていた。

```js
placed.forEach(p => chars(p.text).forEach(ch => all.push(ch)));   // ← 交差を二重に数える
```

2つの語が「せ」で交差すると、盤面のマスは**1つ**なのに、語の文字としては**2つ**に見える。
記号は1マスに1つしかふれないので、実際には足りない。

**対策**：**マス単位**で数える（交差したマスは1回だけ）。

```js
function cellCharCounts(placed) {
  const map = new Map();
  placed.forEach(p => { /* r,c,dir から1マスずつ key に入れる */ });
  const out = new Map();
  for (const ch of map.values()) out.set(ch, (out.get(ch) || 0) + 1);
  return out;
}
```

あわせて、盤面を組む点数にも「キーワードのマスが足りないぶんの減点」を入れた
（必須語 200000点 ＞ **キーワード不足 −50000点** ＞ 語数 10000点）。
検証：同じ条件で組み直しを4回試して、直す前は2回失敗、直したあとは4回とも成功。

**教訓**：クロスワードで「文字が何個あるか」を数えるときは、
**語の文字数ではなく盤面のマス数**で数える。交差は1マス。

## 2026-08-30 「こさいん」の中に「さいん」が埋もれて、置いていないのに配置済みになった

**症状**：ワードに「さいん」と「こさいん」を登録して自動で組むと、
盤面のどこにも「さいん」が見えないのに、①ことばのワードが**配置済み（緑）**になる。

**原因**：置けるかどうかの判定に「**同じ向きの語と重ならない**」という条件が抜けていた。

- 「語のすぐ前後は空いていること」は見ていた（`canPlaceStrict` / `validate` の両方）
- ところが **先に「さいん」を置き、あとから「こさいん」を上にかぶせる**と、
  こさいんの前後は空いているので合格してしまう
- 結果、さいんはこさいんの一部になり、盤面からは「こさいん」としか読めない

**対策**：
1. 自動生成（`canPlaceStrict`）に `dmap`（マス→通っている向き。1＝ヨコ／2＝タテ）を渡し、
   **同じ向きの語が通っているマスには置けない**ようにした。
2. 手で置くとき（`validate`）も、同じ向きの語のマスと重なったら
   「同じ向きの『こさいん』と重なります」と理由つきで断るようにした。
3. 前に作った作品に埋もれた語が残っていても気づけるよう、
   **語の前後に文字が続いていたら警告**を出すようにした（読める語になっていない、の意味）。

検証：8回組み直して埋もれ0件（直す前は同じ条件で発生）。「さいん」は8回とも別の場所に置けた。

**教訓**：「語の前後が空いているか」だけでは足りない。**あとから置く語が、
前に置いた語を飲みこむ**ことがある。同じ向きの重なりは常に禁止でよい。

### [2026-09-07] セッション193 — 迷路謎メーカー ほんとうの1ページ統合＋4段が作れない原因を直す

**指摘への対応（5点）**

| 指摘 | 対応 |
|---|---|
| マスの数の入力欄が大きすぎてかぶってる（12×12みたいなやつ） | `input[type=number]{width:100%}`（型セレクタ）が `.num{width:74px}`（クラス）に**優先度で勝っていた**のが原因。`input[type=number].num` にして幅を効かせ、ラベルを inline-flex にした |
| 色絞り→スタゴル→線けし→色絞り の4段が18×18でも作れない。本当に計算上むりなのか、余分な制限があるのか | **余分な制限**だった。失敗地点に印をつけて数えたら3つ重なっていた（下記）。0/5 →**84/84**（14通り×3サイズ×6回） |
| 線けしは、必ず元より短い・全然ちがうルートが開拓されるようにしてほしい | 近道さがしを「となり合う2マスの壁1本」から「壁を3本まで消して離れた2点をまっすぐつなぐ通路」に拡張。**前の道に無いマスを通ること**を採用条件にした（満たさなければ迷路ごと作り直す） |
| ページの統合とはそういうことではない！！簡単作成のUI/UXに詳細の機能を入れていく感じ | 前回は「下にぶら下げた」だけだった。**結果のPNG画像をやめて、編集用の盤面そのものを結果の場所に置いた**。見ているものをその場で直せる |
| 迷路が100%表示で全体が見える＋問題と切り替えボタンも一緒に見えるようにして | 高さを「箱ぜんたい」ではなく「迷路が映る部分」にかけた。iPad横で 138px→384px、スマホで 79px→216px |

**4段が作れなかった原因（3つ重なっていた）**

1. 必要マス数を「**次の1段ぶん**」でしか見ていなかった → うしろの段から逆算（`stageNeeds()`）
2. 近道の候補が壁1本だけ → 90回中51回が候補ゼロ。通路まで広げた
3. 置き場所さがしが後戻りしない貪欲法 → 深さ優先＋後戻り（上限つき）に

**あわせて速くした：** START/GOALの置き場所を1組ずつ解いていたのを、
START側から1回だけ距離をひろげてふるい分ける方式に（`distFrom`/`tooShort`）。
**33.3秒 → 1.3秒**（solve の呼び出し 64221 → 1997）。

**検証：** node ＝ 組み合わせ14通り×（12・14・18×18）×6回＝84/84、
線けし24件すべてで「4マス以上短く・前は通らなかったマスを通る」、
色/読む順18本・まぎれ文字10本も合格。
ブラウザ ＝ 新設の統合テスト25本＋既存の編集操作29本＋かんたん作成11本、いずれも2回連続で全通過。
iPad縦・iPad横・PC・スマホの4サイズでレイアウトを実測＆目視。

**追加の指摘（同じセッションの後半）**

| 指摘 | 対応 |
|---|---|
| 1段目の答えとルートが変わるとき、元のルートが残って見づらい | 見るだけの盤面に切りかえても `renderOpts.routePaths`（設計図で描いたルート）が残り、その段の通り道と重なっていた。`editor.js` の描画で、見るだけのときは重ねないようにした |
| 「作れません」のとき何が問題か・どうすればよいかを出してほしい | `makeOne()` が行きづまった場所を数え（seed/stage:◯/place:N/read:N/check）、`build()` がいちばん多かった場所から「何が問題か」＋「直し方（番号つき）」を返す（`explainFail`）。「迷路を大きくする」は上限20×20に届いていないときだけ提案する |
| （予防）作る前に入る文字数を知りたい | `capacity()` を新設。②の下に「文章は合計20文字。この迷路(12×12)には76文字まで入ります（あと56文字）」と常時表示。はみ出すと赤で必要な文字数と盤面サイズを出す。断り文句と同じ式を使う |

**「せんをけすが最後にあるとだめなのか」への答え：** 位置の問題ではない。
線けしは「前の段の道」に近道を作るしかけなので、その道が短いと近道の余地がないのが原因。
わき道を増やすか、前の段の文章を長くすると通る。5段（スタゴル2回＋線けし）は20×20で作れる。

**使う人目線・システム目線のレビューをサブエージェント2体に依頼中**（重複・不要・要修正さがし）。

**きっかけ：** 伊神さんから「かんたん作成のUI/UXがとても良い。詳細修正を統合して、
最終的に詳細修正ページを無くしたい」という大きな方向性の相談と、細かい指摘2点。

| 指摘 | 対応 |
|---|---|
| 赤→青→スタゴル変更にすると次の段が青を引き継ぐが、スタゴル変更後は赤に戻したい。ただし個別に色を変えたい場面もある | `stageColors()` の既定ルールを作り直し。「読み方を変えて読み直す」は次の色へ、「線を消す／STARTが変わる／GOALが変わる／STARTもGOALも変わる」は既定で赤にもどす。かんたん作成②の各段に「色：」のえらぶ欄を追加し、個別に上書き可能に |
| 読む順番（うしろから・左→右等）が全段共通にしか適用できない。段ごとに変えたい | `readOrder(parts, opts, 段番号)` に段番号を渡せるようにし、`opts.stageOrder[段番号]` があればカードの既定より優先。②の各段に「読む順：」のえらぶ欄を追加（読む順カード選択時のみ表示） |

**設計上のポイント：** 「線を消す」は近道が前の道の一部を必ず使い回すので、直前と同じ色だと
紙の上で見分けがつかない（→直前が赤なら次の色に進める例外あり）。一方「STARTやGOALが変わる」は
前の道と重ならない新しい場所を選ぶ構造なので、同じ色のままでも問題ない（既定で赤に戻して、
直前がすでに赤ならそのまま引き継ぐ形になる）。理由が違うので、ガードのかけ方を分けた

個別の色上書きで色の並びが不連続になる可能性が出たため、`sameColorRunStart/End`
（連続していることが前提）を `sameColorBefore/After`（連続していなくても同じ色の段を
すべて拾う）に一般化。既定どおりの並び（連続）では結果が変わらないことをテストで確認ずみ。

**検証：** node 18本（色ルール・個別上書き・読む順上書きの単体テスト）、
既存の隣接検証（dbg3.js）・7段ビルド（stage7.js）・幅広い組み合わせ回帰（combo3.js、
赤だけ〜スタゴル×2まで7パターン×4回）すべて合格。ブラウザ11本（wiztune1.js：
UIに色・読む順のえらぶ欄が正しい段数だけ出る／上書きが反映される／自動作成に反映される）
すべて合格。README.md に新ルールと個別上書きの使い方を追記。

ふつう : 迷路を作る → 人が解く
これ   : 正解ルートを描く → その道が「たった1本の最短ルート」になる迷路を自動生成

**実装した主なもの**
- `generate.js`：正解ルートを種にしたランダムPrim法。閉路を作らないので**正解が唯一の最短になることが構造的に保証される**
- `engine.js`：最短経路＋**経路の本数**を同時に数えるBFS。一方通行（有向）・○全通過（ビットマスクBFS）・順番指定・×回避・ワープに対応

- `steps.js`：STEPの連鎖。**設計図(Maze)を毎回複製してから変換をかける**ので、STEPをいじっても設計図が壊れない
- `render.js`：**描画関数は1本だけ**。画面・印刷・PNG・プレイヤー画面が同じ関数を呼ぶ
- 自動検証：到達可能／最短一致／最短が複数／○全通過／×回避／一方通行の詰み／ワープの近道／STEP間の状態変化／想定こたえとの一致
- 白黒印刷対応（色→線のもよう＋文字の飾り＋凡例）、PNG保存、プレイヤーモード

**検証（合計583項目・全部パス）**
- ロジック：迷路生成の一意性を100回試行、一方通行・○×・ワープ・壁無効化、反転回転の可逆性、囲まれた領域、転写

  - 手動で常に決め直す「キーワードが入るように、記号の位置は自動で決め直す」チェックも追加
  - 探索そのものも改良：文字が決まっているわくから先に埋める／キーワードの不足文字を含む語を優先／
    残りマス数で足りないときは枝を切る（`shortage()`）／最後にキーワードの文字がそろっているか確認

**④「盤面を全部消して、ワードとキーワードを登録しても作れない」**
- ③と同じ原因（記号の位置の固定）。③の対処で解決
- 検証：盤面を空にする → ワード「たいよう」＋キーワード「しんぶん」→ 成功
  （記号を読むと「しんぶん」。形も完全に一致）

**⑤ あわせて**
- 型モードのワード一覧で、辞書から自動で入った語に「**辞書から自動**」の印を付けた
  （＝自分で登録した語と区別できる。「登録ワードは今のぶんだけ」というユーザーの指摘への対応）

**検証（Playwright・すべて成功）：**
| ケース | 結果 |
|---|---|
| 記号ゼロ＋キーワード「がっこう」 | 記号を読むと「がっこう」・形一致 |
| 記号そのままで入るキーワード「たいよう」 | 記号は1つも動かず・形一致 |
| キーワード自動（登録ワード1語） | 「こまかい」＝辞書語・形一致 |
| 盤面を空にする＋ワード＋「しんぶん」 | 記号をふり直して成功・形一致 |
| 2文字を手入力／候補タップ | どちらも理由つきで登録拒否 |
| ふつうモードの自動作成 | 今までどおり9語で成功（影響なし） |

**教訓・知見：**
- **同じ操作の入口が複数あるときは、判定を1つの関数にまとめる**（今回は「ワード登録」が3経路あった）
- **状態を保存したら、読み込む側でも必ず引き継ぐ**。今回は保存はできていたのに、開くときに捨てていた
- 制約を固定して探索するときは、**制約そのものを動かせる余地**（記号の位置）を用意しておくと、
  「ふつうならできるのに、こっちだとできない」が起きにくい

**次のアクション：**

### [2026-08-31] セッション169 — ことばかける君 記号が作り直しで消える件の対処

**報告：** 「③しあげで記号の位置を変えても、②自動で生成すると戻される」

**調査結果：**
- **型モードでは消えていなかった**（検証：記号を動かして「この型で作る」→ 位置は完全に保持）
- 消えるのは**ふつうモードの「作り直し」系**（runGenerate／autoBuild／buildWithRequired）。
  形そのものを作り直すため `state.marks = {}` していた（仕様どおりだが、**予告なし**だった）

**対処：**
- 作り直し系の入口に確認を追加（記号が1つでも付いているときだけ出る）
  「作り直すと、いまの記号（キーワードの位置）は消えます。よろしいですか？
  　※記号の位置をそのままにして中の言葉だけ変えたいときは「🏠さいしょ→📐同じ形で作る」を使ってください。
  　（まちがえて消したときは「元に戻す」でもどせます）」
- キャンセルすると盤面も記号もそのまま。OKで作り直したあとも「元に戻す」で復活することを確認

**検証（Playwright）：**
- 型モード：記号を動かして「この型で作る」→ 記号は変更後のまま保持（成功ケースで確認）
- ふつうモード：確認が出る → キャンセルで記号保持 → OKで消える → 元に戻すで復活

**教訓・知見：**
- 「戻される／消える」の報告は、**どのモードのどのボタンか**を切り分けてから直す。
  今回は仕様どおりの動きだったが、**予告なしに消える**ことが問題だった
- 破壊的な操作は、代わりの手段（今回は型モード）を確認ダイアログの中で案内すると、機能の発見にもつながる

**次のアクション：**

### [2026-08-31] セッション168 — ことばかける君 型の引き継ぎ・記号の位置変更・検索の文字数グループ・ダブルタップ拡大の停止

**作業内容：**

**① 型モードを「つづきから」でも引き継げるようにした**
- 前：型（shapeLock）はページを開いている間だけの状態だったため、
  「つづきから作る」を押すと、同じ形なのか新規なのか分からなくなっていた
- 後：型を作品データに保存（serialize/applyData）し、リロードしても残るようにした
- さいしょページの「つづき」ボタンを「↩ 📐 型のつづきをする（形は固定のまま）」に変え、
  「『◯◯』と同じ形／わく◯個」と明示
- 「ふつうに作る」を選んだときは「型をやめる／型のつづきをする／やめる」を確認（うっかり解除の防止）
- 作品を開く・新規作成のときは今までどおり型を外す（「元に戻す」では外れない）

**② 記号（キーワード）の位置を変えられるようにした**
- 型パネルに「記号（キーワード）の位置を変える」「型の記号にもどす」を追加
- 記号の数を変えると、キーワードの必要文字数の案内もその場で更新（lock.markCount → 実際の記号数を参照）
- 記号の位置を変えただけでも「この型で作る」が押せるようにした（新しい問題になるため）
- 勝手に記号を戻す処理はやめ、「型の記号にもどす」ボタンで明示的に戻す形にした

**③ ワード検索を「文字数ごと」に表示（ユーザー提案）**
- 型モードでは、型に入る文字数だけを長さごとに分けて表示
  見出しは「3文字（0/2）　あと 2語」（そろうと緑）
- 各長さ最大24語ずつ出すので、長い語ばかり・短い語ばかりに偏らない

**④ ダブルタップでの拡大を止めた**
- html/body だけでなく、ボタン・チップ・入力欄などにも touch-action: manipulation を指定
- 盤面（ドラッグを拾うところ）は今までどおり touch-action: none

**⑤ ついでの修正**
- 型に入った直後は登録ワードが空になるため、かなの種類（ひらがな／カタカナ）の自動判定が
  カタカナに倒れて、検索結果がカタカナで出ていた → 盤面の語・型に覚えたかなも見て判定するようにした

**⑥ 検証（Playwright）**
- リロード後も型が残り、「型のつづきをする」で①ことばへ復帰／「ふつうに作る」で確認が出る
- 記号を1つ消す・足すと案内のキーワード文字数が即時更新／「型の記号にもどす」で復元
- 記号を足しただけで作成 → 5文字のキーワード「しょうきょ」（辞書語）で成功
- 検索は「2文字（0/2）」「3文字（0/2）」「4文字（0/1）」の見出し付きで表示・ひらがなで表示

**教訓・知見：**
- モード（状態）を作ったら、**保存・復元まで含めて1セット**。セッション限りの状態は
  「つづきから」で必ず迷子になる
- 制約つきの検索は「条件を絞る」より「**条件ごとに分けて見せる**」方が、必要数との対応が取りやすい

**次のアクション：**

  ダブルタップ拡大が止まっているか）

### [2026-09-08] セッション196 — 迷路謎メーカー 「線を消す」を必ず効かせる／迷路が行方不明にならないようにする

**指摘への対応（2点）**

| 指摘 | 対応 |
|---|---|
| 「線を消す」は必ずルートが変わるようにして。もともとのルートでは赤い線があることによって進めず遠回りしている。線を消すともっと短いルートが見つかって拾う文字が変わる。**壁を追加するなどして「必ず」そうなるように** | **さがすのをやめて、こちらから作る**ようにした。いまの道の上に壁を1本足して赤くぬれば、その線が近道をふさいでいる状態が最初から作れる。行き止まりになるときだけ、先に4マス以上長いまわり道をひらく |
| 迷路は基本100%の全体表示。そのとき迷路上でスクロールできないようにして。ズーム中もスクロールの上限を。**ページのスクロールの邪魔になったり、迷路が行方不明になる** | 移動できる範囲をおさめる `clampView()` を1つ作り、**描くたびに必ず通す**。100%表示ではまん中に固定＝動かない。ホイールは横取りせずページにゆずる |

**① 「線を消す」を作る側にした（`packages.js` の `forceDetour`）**

前は「できた迷路の中から、消すと近道になる壁をさがす」やり方だった。
うまくいくかどうかが迷路の運まかせで、見つかっても「角を1つ切るだけ」のことがあった。

いまは逆に、ほしい状態から逆算する。

1. いまの道の上の辺を1つえらび、**壁を足して赤くぬる**（＝これが消す線）
2. 足すと行き止まりになるときだけ、先に**4マス以上長いまわり道をひらく**

これで「消す前＝遠回り／消したあと＝みじかい別の道」が、さがす前から決まる。
わき道のある迷路では 1 だけで足りる。

**採用の条件：** 4マス以上みじかくなる／前の道に無いマスを**3つ以上**通る／
消す前も後も最短が1本で差4マス以上／次の段の文字が置ける長さが残る／**前の段の道が変わらない**。

**いちばん危なかったところ：足した壁は「最初から」立っている**

段を進めるしくみは「1枚の盤面を段ごとに解き直す」形なので、
3段めで足した壁は**2段めの盤面にも立っている**。
そのせいで「線を消す」段が2つあると、2つめで足した壁が1つめの効き目を消し、
**1段めが『線を消しても道が0マスしか変わらない』段**になっていた（実測で発生）。

対策は2段がまえ：
- 段ごとの盤面のひかえ（`boards[]`）で、候補を採用する前に**前の段の道が変わっていないか**検算
- 作りおわったあとに、**すべての線けし段の効き目を数え直す**。1つでも欠けたら迷路ごと作り直す

**ついでに直った：まわり道さがしが「早く着きすぎた」だけであきらめていた**

`findDetour` は目あてに着いた時点で長さを判定し、短ければ **null を返して探索ごと終了**していた。
出発点と目あては数マスしか離れていないのですぐぶつかり、**207回中205回失敗**していた。
短すぎる到着を「行き止まり」あつかいにして必ず後戻りする `detourPath` を新設し、1% → 57% に。

**② 迷路の表示（`editor.js`）**

| 状態 | 動き |
|---|---|
| ぜんたいが見えている（100%） | まん中に固定。指でもホイールでも動かない |
| ぜんたいが見えている＋ホイール | 迷路をつかまえず、**ページのほうがスクロール**する |
| ズームインしている | 動かせるが、盤のはしが画面のはしより内側に入らないところで止まる |

移動の入口が6つ（指・ホイール・ピンチ・ズームボタン・「全体」・画面サイズ変更）あるので、
それぞれの後ろに範囲チェックを入れるとどれかを取りこぼす。
**`draw()` の先頭で必ず `clampView()` を通す**形にした。
盤のまわりの余白を指でなぞったときは、100%表示ならページを縦に動かす
（キャンバスは `touch-action:none` なので、こちらで動かさないと iPad でページがスクロールできない）。

**検証**

  ＝遠回りしていた」「赤い線は必ず消したあとの道の上にある＝近道をふさいでいた」を満たした

  4段スタゴル＋線けし18×18 **10/12 → 12/12**（6.5秒→4.3秒）、

**教訓・知見：**
- **性質がほしいなら、探すのではなく作れないかを先に考える。** 「条件を満たすものをさがす」は
  母集団しだいで見つからない。「満たすように盤面のほうを変える」なら必ず作れる。

### [2026-09-08] セッション195 — 迷路謎メーカー 答えの文字を固まらせない／「最短ルートが複数」をその場で直す

**指摘への対応（2点）**

| 指摘 | 対応 |
|---|---|
| 答え「わかる」の3文字が連続して置かれ、迷路を解かなくても答えが分かってしまう。できるだけ連続を避け、はじめ・なか・おわりに分けたい（はじめより、なか・おわりを多めに） | 置き場所の目あてを「空きマスの何番めか」から「**道すじのどのあたりか**」に変えた。道を3つに分けて重み **2:3:3** で配る（はじめを軽く）。あわせて**道すじのすきま**（`GAP`）を条件に加え、となり合うマスには置かない |
| 「最短ルートが複数あります」と出たとき、直し方が分からない | 警告のとなりに「**🔧 わき道をふさいで1本にする**」ボタンを出した。押すと、残したい道の上にない「最短の辺」だけを壁でふさぐ（`generate.makeShortestUnique`）。**壁を足すだけ**なので道は短くならず、通れなくもならない。↶ でもどせる |

**① 答えの文字を固まらせない（`packages.js` の `placeOnFree` / `fillGaps`）**

3つ重なって「わかる」が3マス並んでいた。

1. **目あてが「空きマスの番号」だった** … 空きマスが少なくてかたまっていると、そのかたまりの
   中で均等にならべることになり、道の上ではとなり合う。→ `sectionAt()` / `wantCell()` で
   道すじの位置を目あてにした
2. **道すじの距離を見ていなかった** … 盤の距離 D≥2 だけでは、ぐねぐね曲がった道で
   となり合うマスが通ってしまう。→ `tryFit(D, GAP)` で道すじのすきまも見る（GAP≥2）
3. **間の1マスが空白だった** … GAP=2（間が1マス）を許すと「わ□か□る」で読めてしまう。
   → 文字と文字の**まん中のマスを `mustFill`** として、こさの設定に関係なく先に埋める

**ついでに直った：** 空きマスが少ないとき、目あて位置がちがう文字でも同じ空きマスに寄って
探索の目じるしがつぶれ、成り立たない並びばかり試していた。`wantIdx` を
`[i, free.length-(残り文字数)]` に収めた。行きづまりからのやり直しが増えるので
探索の上限も `4000` → `4000 + 空きマス×文字数×20`（上限40000）に。

**② 最短ルートを1本にする（`generate.makeShortestUnique`）**

STARTからの距離 `dS` とGOALからの距離 `dG` を1回ずつ測ると、
「どれかの最短ルートが通る辺」は `dS[a] + 1 + dG[b] === 最短の長さ` で見分けられる。
そのうち**残したい道の上にない辺だけ**をふさぐ。一方通行・ワープがあるときと、
残したい道がそもそも最短でないときは、理由を出して断る。

**検証**

- 答えの置き場所（node・新規 `clump3.js`）：作れた迷路の**となり合う答え文字181組すべて**で
  道すじのすきま2マス以上（内わけ すきま2が9組・3が44組・4以上が128組）。
  文字と文字のあいだが空白のままの組は**0件**。
  こたえの段の位置は **はじめ14 / なか17 / おわり21** で、ねらいどおり はじめが最少
- 1本にする（node・新規 `uniq1.js` 12件／ブラウザ・新規 `fixbtn1.js` 14件）：
  3432通り → **1通り**、最短の長さは14のまま、壁 40 → 138（98か所ふさいだ）、↶ で40にもどる
- **作りやすさは落ちていない**（同じ乱数の種で前後を比較・各20回）：
  5段16×16 5/20→5/20、5段18×18 2/20→3/20、3段14×14 20/20→20/20、2段線けし 20/20→20/20。
  ただし**時間は約2倍**（2.5秒→4.7秒。行きづまってからのやり直しが増えたぶん）
- 回帰テスト10本すべて通過（onepage2 25・interact 29・route1 6・fixbtn1 14・paper1 6・
  erase1 8・nohide1 10・color2 18・verify3 7・uniq1 12＝**135件 失敗0**）、ベンチ 56/56

**分かったこと（伊神さんへ）：** 5段で「読み直し」ばかりを4回つなぐと、
1本の道に43文字を並べることになり、16×16では4回に1回くらいしか作れない。
このときは断り文句が「3段めの文章（10文字）を短くする」「まわりの文字の量を少なめに」と
出るので、そのとおりにするか、**あいだにスタート/ゴール変更や線けしを入れて道を変える**と
文字が分散して作りやすくなる。

**教訓・知見：**
- **「均等にならべる」は、何に対して均等かで結果が変わる。** 入れ物（空きマス）に対して
  均等にすると、入れ物が偏っているときに出力も偏る。人が見るもの（道すじ）を基準にする
- **直し方が分からない警告は、警告ではなく手間の押しつけ。** 直し方が計算で決まるなら、
  警告のとなりに直すボタンを置く
- **少ない回数の成功率比較は信用しない。** 8回で「0/8 → 2/8」と見えたものが、
  乱数の種をそろえて20回にすると「5/20 → 5/20」だった

**次のアクション：**
- iPad実機テスト待ち（🔧ボタンが押しやすいか／答えの文字の散らばり方が
  問題として自然か／5段を作るときの待ち時間（約5秒）が許せるか）

### [2026-08-31] ことばかける君 同時モード — 共通ワードの位置を自由に／登録ぐあいの表示バグ修正

**プロジェクト：** ことばかける君 (`projects/crossword/dual.html`)

**1. 「共通ワードを同じマスに置く」を①②③どれでも切りかえ可能にした**
- これまでは①②で必ず固定、③だけ切りかえ可だった
- オフにすると「**同じ語が A と B でちがう場所に入る**」＝それ自体が仕掛けになる

  直したときに2つ問題が出て、どちらも実測で見つけた：
  - **オフにしても実際には同じマスのままだった。**
    組み方の点数で「A と B の文字が同じマス」を加点していたため、
    共通ワードどうしの組（＝同じマス）が常に最高点になり、60通り作っても必ずそれが選ばれていた
    → オフのときは「ちがう相手と組ませた案」を加点して釣り合わせた
  - **今度は作れないことがあった。**
    交差できない組み方が高得点になってしまったため
    → 交差できるかどうか（cross）を最優先（×100）にした
- 結果：オンなら必ず同じマス。オフなら入れかえられるときは別マス、
  入れかえると交差できない語では**同じマスに戻して作る**（作れなくならない）

**2. 「A と B の登録ぐあい」に、辞書から足した語まで混ざっていた（バグ）**
- 「同時に作る」を押すと、辞書から足した語も登録ワードに入れている（カギを書けるようにするため）
- そのせいで、2語ずつ登録したはずが「A 12語 ／ B 12語」と表示されていた
- 直し：辞書から足した語に `auto` の印を付け、登録ぐあいの数からは外した。
  ワード一覧には「辞書から」の印を出し、自分で登録し直したら印が外れるようにした

**検証（実ブラウザ）：**
- A・B とも「かさ・さか」でオフ → 6回中6回、同じ語がちがうマスに入った
- A・B とも「さくら・あさひ」でオフ → 入れかえると交差できないので3回中3回同じマス、**作れず0回**
- オンはどのモードでも必ず同じマス
- 「同時に作る」後も登録ぐあいが「2文字 A1／B1・4文字 A1／B1」のまま（辞書追加28語は注記のみ）
- 既存機能の再確認も通過（モード①②③・自動キーワード・見くらべ・印刷・保存復元・作れない理由）

### [2026-08-31] ことばかける君「同時に2つ作る」— キーワード未登録時の挙動を決定

**プロジェクト：** ことばかける君 (`projects/crossword/dual.html`)

キーワードフィールドを空のままにしたとき、できた盤面から自動でキーワードを探す機能に対して、**基準を実測に基づいて決定**しました。

**測定方法**
36回クロスワードを生成し、各盤面サイズで「見つかった割合」を計測。

**測定結果と基準決定**
従来の勘（1文字あたり4マス）が4文字・5文字で甘かったことを確認。実測に基づき以下に修正：
- **4文字キーワード**：20マス以上（勘は16マス）
- **5文字キーワード**：32マス以上（勘は20マス）
- **3文字以下**：10マス以上（〜11マスでも100%だったため）

成功率表：
```
マス数        2文字   3文字   4文字   5文字
〜11マス      100%    100%    50%     0%
12〜19マス    100%    100%    75%    50%
20〜31マス    100%    100%   100%    79%
32マス以上    100%    100%   100%   100%
```

**実装のポイント**
- **門番として使わない**：基準に足りなくても一度は試す（探索は数十ミリ秒の軽い処理）
- **盤面を先に育ててから探す**：ねらう文字数に必要なマス数を計算し、先に辞書から語を足して盤面を成長させてからキーワードを探索
  - 同じ2語でも、16語・69マスまで育てれば「A『しょくじ』/B『じょうし』」が決まる（実測 0.18秒）
- **総当たり→制約条件で絞込**：総当たりなら1万語×1万語＝1億通りだが、盤面の「A の文字→取れる B の文字」表を先に作ると数十〜数百ミリ秒に短縮
- **見つからないときは理由を数字で**：「いま28マス／目安32マス」のように、なぜ見つからなかったのかを明示

**パフォーマンス改善**
上限付き生成が毎回 9 秒かかっていたのを、条件満たした時点で切り上げるようにしました。
- **実測：9000ms → 120〜350ms**

**検証（動作確認済み）**
- 空のキーワードで作成を実行 → マス数に応じた基準で探索実行
- 基準値より小さい盤面でも試す → 見つかれば採用・見つからなければ理由を表示

**次のアクション：**
- **iPad実機テスト待ち**（2列入力の窮屈さ・A/B切りかえ・見くらべ画面・生成待ち時間）

## 0. これは何のプロジェクトか

オフ会用の大人数パーティゲーム集。ホストPCをスクリーン投影し、参加者は各自のスマホをコントローラーにして遊ぶ（Jackbox型）。

- 公開URL：https://gamigamiigami.github.io/Workspace/projects/oshiking/
- 遊び方・各ゲームのルール詳細 → `README.md`（このファイルとは役割が違う。README＝遊び方、HANDOFF＝開発を続けるための情報）

## 3. アーキテクチャの勘所（次に手を入れる人向け）

### 3.1 ホスト⇔コントローラーの二役構成
- パラメータ無し → ホスト画面（`host_init()`）
- `?room=<peerId>` → コントローラー画面（`ctrl_init()`）
- 通信：PeerJS（無料公開クラウド）。QRはqrcode-generatorで端末内生成。

### 3.2 入力は`pressHandler`に集約（最重要パターン）
```js
let pressHandler=null;   // 各ゲームがゲーム開始時に差し替える
let minusHandler=null;   // カウンター系ゲームが使う「−1」受け口
function endInputs(){ pressHandler=null; minusHandler=null; clearCpu(); broadcast({type:"enable", on:false}); }
```
- コントローラーの`press`メッセージ／CPUのタイマー／ホストPC本人プレイ（`hostPress()`）は**全部同じ`pressHandler(id)`を呼ぶ**。入力経路が完全に統一されているので、新しいゲームを追加してもここを壊さない限り全経路が自動的に動く。
- ゲーム終了時は必ず`endInputs()`を呼ぶこと（呼び忘れると次のゲームに古いハンドラが残る）。

### 3.3 コントローラーのUIモードは3種類
`broadcast({type:"prompt", ui:"tap"|"cycle"|"counter", options:[...], enable:true})` で指定。
- **tap**：普通の1ボタン
- **cycle**：押すたび選択肢が切り替わる（`options`配列指定、省略時はグー/チョキ/パーにフォールバック）。3すくみ・少数決・偶奇投票で使用。
- **counter**：押すたび+1、専用の「−1」ボタンも表示される（果物カウントのみ使用）。−1は`minusHandler`経由でホストの実カウントとも同期する（表示だけのローカル処理にしないこと＝過去にそこが甘いと表示とスコアがズレるバグになりやすい）。

### 3.4 新しいミニゲームを追加する3点セット
1. `GAMES`配列に1行追加（`key`, `title`, `rule`, `ui`は表示用メタ情報のみで実際の入力方式は各ゲーム内のbroadcastで決まる）
2. `playGame()`の分岐に1行追加
3. `async function gameXxx(){...}`を実装。戻り値は**順位つきID配列（best→worst）**。`showResult()`が上位3人に3/2/1点。

### 3.5 多ラウンド系ゲームの注意点（過去にハマった）
`addCountdown()`は呼ぶたびに新しい`.countdown`要素を**追加するだけで前のを消さない**。単発ゲームは問題ないが、`minority`・`evenodd`のような多ラウンドループでは、ラウンドの頭で明示的に前回の表示を消すこと：
```js
const arenaEl=$("stage").querySelector(".arena");
// ループの先頭で：
if(arenaEl) arenaEl.querySelectorAll(".countdown").forEach(el=>el.remove());
```
これを忘れると古いラウンドの文字が画面に重なって残る（このバグは本セッションで発見・修正済み。新しい多ラウンドゲームを作るときは最初からこのパターンを踏襲すること）。

## 4. サウンド＆演出エンジン

`sfx(name)` でWeb Audio生成音を再生（ファイル不要・オフライン動作・GitHub Pages以外の閉域網でも鳴る）。
- トーン系：`press`/`count`/`tick`/`tickHi`（メトロノーム）/`go`/`good`/`lose`/`win`/`fanfare`
- ノイズ系（2026-07追加、`noise()`のバッファ生成）：`slam`（タイトルのドン！）/`whoosh`（画面切替）/`drum`（ドラムロール約1.3秒）/`applause`（拍手）
- `sfxInit()`をユーザー操作（参加ボタン押下・メニュー表示等）のタイミングで呼ぶこと（ブラウザの自動再生ポリシー対策。呼び忘れると音が鳴らない）。
- `partyBurst()`（紙吹雪）／`screenFlash()`（画面フラッシュ）は勝利・優勝時に使用。

### 4.5 ビジュアル層（2026-07-02 全面リニューアル）

ゲームロジックには手を入れず、**表示レイヤーだけ**を番組/Jackbox風に刷新した。次に触る人向けの要点：

- **アバタートークン**：プレイヤーは `makeToken(p,size)` で生成（顔絵文字 `p.face`＋色グラデ＋名前タグ）。`id="dot"+pid` と `.dot` クラスは従来のまま＝`flash()`・`.mash-badge`・`.dead` がそのまま効く。**新ゲームでトークンを自作せず必ず `makeToken()` を使うこと。**
  - `p.face` は `FACES` 配列から参加順に自動割当（join/addCpu/addHostPlayerの3箇所）。`welcome` メッセージでスマホにも送っている。
  - 顔絵文字を差し替えたいゲーム（例：ガンマンの🎯）は `dot.querySelector(".face").textContent` を書き換える（`dot.textContent=` で潰すと名前タグごと消えるので禁止）。
- **タイトルカード**：`showGameIntro()` が `GAMES` の `icon`/`color` を使う（`--accent` CSS変数でテーマ色が変わる）。新ゲーム追加時は `GAMES` 行に `icon` と `color` も必ず入れる。
- **表彰台**：`showResult()` は3位→2位→1位の順に `pod.show` を付けて発表（ドラムロール→1位でファンファーレ＋紙吹雪）。順位配列の意味は従来どおり。
- **プレイヤー名のHTML埋め込みは必ず `esc()` を通す**（外部入力なので）。
- スマホ側は `--mycolor` CSS変数で自分の色にテーマ化、`vibe(ms)` でバイブ。

## 5. このセッションで直した主なバグ・設計判断（再発防止のため記録）

1. **3すくみの勝敗判定が逆だった**：「2種類の手しか出ていなければ勝つ方が勝ち」の判定式が`(m+2)%3`（負ける手の予測）になっており、実際には**負け手が勝者として扱われるバグ**があった。`(m+1)%3`（勝つ手）に修正。あわせて、8人前後だと本物ルールでは「あいこ」だらけになることが判明したため、リアルな「あいこでしょ！」の自動再戦（最大4回）を追加した。
2. **多ラウンドゲームの古い表示が消えず重なる**：§3.5参照。
3. **カウンター系の−1操作がホストに伝わらないと表示とスコアがズレる**：`minusHandler`という専用の受け口を新設し、ネットワーク経由でホスト側の実データも同期するようにした。ローカル表示だけ更新する実装は避けること。
4. **丸太ジャンプの当たり判定は「厳密な瞬間ヒットボックス」だと不評だった**：到達予想時刻±ファジー幅の判定に変更し、連打・複数回ジャンプを許容する方式にした（`FUZZ`変数）。シビアな判定を作るときは、必ず実際にCPU多数でヘッドレステストして生存率を確認すること（本セッションでは8人中平均7人生存が目安になった）。

## 7. 検証方法（実機がなくてもここまでは確認できる）

サンドボックスからPeerJSの実通信は試せないため、以下で代替確認する：

1. **構文チェック**：inline `<script>`を抽出して`node --check`
2. **ヘッドレスPlaywright**：PeerJS/qrcode-generatorをスタブし、`addHostPlayer()`+`addCpu()`でCPUプレイヤーを増やして各`gameXxx()`を直接呼び出す。戻り値の順位配列が重複なし・全員分含むか、`resultDetail`が生成されているか、`pageerror`が出ていないかをチェックする。
   - このセッションで使ったスクリプトは`/tmp`のスクラッチパッドに作成したため引き継がれていない。同じパターンで作り直すこと（`page.route`でCDNをブロック→`window.Peer`をスタブクラスに差し替え→`page.evaluate`内でゲーム関数を直接await）。
3. **コントローラーUIの動作確認**：`?room=FAKEROOM`付きでページを開き、`handleCtrlMessage()`を直接呼んでprompt受信をシミュレート→`tap.onclick()`/`counterMinus.onclick()`を直接叩いて表示が変わるか確認。

**最終確認は必ず実機（PC＋スマホQR）で伊神さんにお願いする。** サンドボックスでできるのはあくまで「クラッシュしない」「ロジックが正しい」レベルの保証まで。
